## Conclusion

**The performance measurements for Amazon FSx for NetApp ONTAP are scattered across separate Spoke repositories, one per topic.** NFS and block are in S3-Burst-on-ONTAP-Files, S3 Access Points latency is in several Spokes, ListObjectsV2 is in Lakehouse-Integrations — the result for one topic is not necessarily in one place.

**This index lays the protocols and topics out vertically and records only the location of each result document, the Spoke-side stage wording, and the kind of environment it was measured in.** Where [the file-protocol resource map](../../ja/reference/file-protocol-resource-map.md) (日本語) and [the block-storage resource map](../../ja/reference/block-storage-resource-map.md) (日本語) index primary sources, this one indexes the **measurement records**.

**This index carries no performance values.** MB/s, IOPS, ratios, p99 and the like are misread when separated from the environment they were measured in. The numbers live in each row's linked document, alongside the conditions.

> **Tier**: `documented` — each row records where the linked Spoke document keeps what it records. A row with no measurement behind it (a theoretical estimate, a measurement tool only, no results document) says so within the row. **This repository has not re-measured any value in this table.** Spoke documents carry no frontmatter stating a Hub `evidence` tier, so the "Spoke-side stage wording" column is a transcription of the terms each Spoke applies ("検証済み", "サイジングの参考値" / sizing reference, "ドラフト" / draft, "hypothesis", and so on), not a mapping onto a Hub tier. The division of labour is in [the cross-repository citation index](../../ja/reference/cross-repo-index.md) (日本語).

## What to assume when reading this index

**Do not rank values measured under different conditions.** The rows below differ from one another in at least one of: generation, placement, provisioned throughput, client, measurement tool, parallelism, connection count, origin type, or object size. For example, the S3 Access Points write figures are in S3-Burst-on-ONTAP-Files (an EC2 `c5n` in the same region, boto3 or `aws s3 cp`) while the read-latency figures are in Observability-integrations and S3AccessPoints-Serverless-Patterns (a Lambda outside the VPC, or a local workstation). Some records share the generation (first generation) and the origin (Internet), but the operation, where the client runs, the measurement tool, and the object size differ — **these are not values on the same footing.**

- **A sample run is not a production estimate.** Many of the linked documents state outright that they are "a sample run from one environment" or "a sizing reference". They are neither a service-level guarantee nor a production estimate.
- **A specific-environment result is not a general service limit.** The numbers here are measured at a specific generation, region, and provisioned value; they do not read as a general service ceiling.
- **This map has not re-measured any value in this table.** It only points to the location.

## Where results live, by protocol and topic

**The columns mean:**

- **Protocol / topic** — one topic per row
- **Result document** — a GitHub blob link to the Spoke relative path. A row for which no result document has been found says so in this column. The links point to the Japanese originals this map was transcribed from and are marked (日本語); some of those documents also have an English counterpart in the Spoke, which this map does not transcribe
- **Spoke-side stage wording** — a transcription of the stage term a Spoke applies to its own document or claim. Not a Hub tier. The source of each term is shown in parentheses:
  - "stage column of the index": the "段階" column of S3-Burst-on-ONTAP-Files's [index of measurement records (verification/README.md)](https://github.com/Yoshiki0705/S3-Burst-on-ONTAP-Files/blob/main/docs/ja/verification/README.md) (日本語). It is a per-document term
  - "verification status": the table in that repository's [verification status](https://github.com/Yoshiki0705/S3-Burst-on-ONTAP-Files/blob/main/docs/ja/verification-status.md) (日本語). It is a per-claim term, and "検証済み" is defined there as reproduced in a real environment
  - "body": the document's own body or opening note
  - A document with no stage term is written as "no stage term", with the limits the document itself states
- **Environment summary** — the **measurement conditions only**: generation, placement, origin type, client type, measurement date and the like. Configuration values (provisioned throughput, SSD capacity and so on) are measurement conditions, not measured values. Transcribed from each Spoke's condition table. Where a field cannot be read, "see the condition table in the document"; where the document does not state a field, "not stated". A document with no condition table says so
- **Hub transcription note** — a link to the Hub-side digest, where one exists
- **What the document itself calls unmeasured** — an **excerpt** of the range that document records as unmeasured, unconfirmed, or out of scope. It is not a full transcription: the items are chosen for their bearing on the row's topic. A document's list can lag behind it, so an item on a list may have been measured in a later section (rows where a disagreement was found are annotated). Items the document does not list are not written. A map-side observation is labelled "map-side observation (date)"

## How to choose — the variables to hold equal before comparing values

**This map does not state superiority across protocols or services.** Two values may be compared only when the variables below are all held equal. Placing values that are not aligned side by side misreads an environment difference as a protocol or service difference. Each variable is one that the linked documents above list as a measurement condition. The right-hand column is how each Spoke's documents treat that variable.

| Variable to hold equal | How the Spoke documents treat it |
|---|---|
| Generation (1st / 2nd) | The provisioned-value, burst and baseline record cites AWS's published 2nd-generation Single-AZ table. The same utilization metric has a different denominator by generation (the provisioned value on the 1st generation, the baseline on the 2nd), and that record notes that values from either generation cannot be set side by side without checking the denominator |
| Placement (Single-AZ / Multi-AZ, HA pair count) | The S3 Access Points read-latency record says results may differ on Multi-AZ and asks for separate verification. The S3-Burst-on-ONTAP-Files block record gives the data LIFs sitting on a different node and port as one reason for not adding block rows to the file-side side-by-side table |
| Provisioned throughput | In the published 2nd-generation specification table, the disk burst allowance and the presence of the NVMe read cache vary with the provisioned value (the provisioned-value, burst and baseline record) |
| Client type and network | The S3-Burst-on-ONTAP-Files records state whether the client is a `c5n.9xlarge` with guaranteed bandwidth or an instance with an "up to" figure. The S3 Access Points read-latency record states the condition where a local workstation's bandwidth capped the result on the client side |
| Measurement tool | The S3-Burst-on-ONTAP-Files records note that rows from the direct VDBENCH and `auto_vdbench` series are not to be mixed, and that `dd` values are not to be set beside VDBENCH tables |
| Parallelism (thread count) | The S3-Burst-on-ONTAP-Files side-by-side table fixes 512 threads. The S3 Access Points write record measures parallelism 1 / 8 / 32 as separate points |
| Connection count (`nconnect` / SMB channels / iSCSI sessions) | The S3-Burst-on-ONTAP-Files records take the number of connections actually established (connections counted with `ss`, counted TCP connections), not the requested value, as the condition |
| Origin type (Internet / VPC) | The S3 Access Points write record says its values are for Internet origin and that VPC origin was not measured with the same procedure |
| Object size | The S3 API record splits its tables into 1 MiB and 8 MiB. The S3 Access Points read-latency record gives 1 MB and 202-byte small files separate sections |

How these variables moved the measured values is in [A single connection measures the client](../domains/performance/notes/a-single-connection-measures-the-client.md), alongside the conditions.
