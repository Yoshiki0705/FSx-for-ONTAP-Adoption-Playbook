# ファイルを消して S3 Glacier 系へ移す用途は戻しを待てるデータに限られ、連携できる AWS サービスの多くはバケット側にしか届かない

Amazon FSx for NetApp ONTAP（以下 FSx for ONTAP）のボリュームから、めったに読まれないファイルを S3 Glacier 系のクラスへ移し、元を消す運用は、どのデータにも合うわけではありません。このノートは、公開された事例と規則の条文から、合う用途と合わない用途を分け、合わない場合の代替と、AWS のサービスや外部の製品が流れのどの段階につながるかを整理します。

このノートで「パターン」と書くのは、別のリポジトリ [FSx-for-ONTAP-S3AccessPoints-Serverless-Patterns](https://github.com/Yoshiki0705/FSx-for-ONTAP-S3AccessPoints-Serverless-Patterns) の [archive-verify-delete](https://github.com/Yoshiki0705/FSx-for-ONTAP-S3AccessPoints-Serverless-Patterns/tree/main/solutions/data-lifecycle/archive-verify-delete) です。設計はこの Hub（FSx for ONTAP Adoption Playbook）で行いました。実測値は、2026-11-26 の 3 つの確認のものです。「5.5 GiB を含む 7 ファイルの通し」（Fargate を通る写しと戻し）、「除外と承認を確かめる通し」（11 ファイルを作って 4 ファイルが選ばれた構成。除外条件、承認の検査、削除と回復の再試行、戻した後の照合。Fargate は通っていない）、「直接呼び出しを確かめる確認」（256 KiB のファイル 8 つ。承認の結び付け）で、値にはどの確認かを付けます。

## このノートで学べること

- オンプレミスの ONTAP の利用者が、冷えたデータをオブジェクトストレージやテープへ移している理由と、移した後にファイルが見えるかどうか
- FSx for ONTAP の新規の利用者と既存の利用者が、冷えたデータについて公開している根拠
- 業界ごとの用途について、データの種類、読まれにくい理由、戻しに待てる時間、保持規則の例、写して消す流れが合うかどうかと、合わないときの代替
- 流れの 12 段階（選ぶ、記録する、写す、照合する、承認する、消す、戻す、検索する、保護する、監査する、通知する、費用を報告する）に、AWS のサービスと外部の製品がどうつながるか。Access Points まで届くのか、アーカイブ用のバケットにしか届かないのか

### 結論

誰のためのノートか。FSx for ONTAP のボリュームに、数か月から数年読まれないファイルがあり、S3 Glacier 系のクラスへ移すかどうかを決める人です。決めるのは次の 3 点です。自分のデータが「写して、照合して、承認の後に消す」流れに合うか。合わないなら何を使うか。連携したい AWS サービスや製品が、どの段階まで届くか。

1. **合うのは、戻しを数時間から 48 時間待てて、元のパスで開く必要のないデータです。** 公開事例で挙がる、生のシーケンサー出力、完了した制作物の素材、公刊後の研究データがこれに当たります。元のパスで開く前提の事例（FabricPool、容量プール、動的リンクを使うもの）は、別の層の話で、この流れは使えません。単一ファイルが 50 GiB を超えると Access Points へ戻せないため、生映像や生のシーケンスデータなど大きなファイルは、パターンが選択から外します（除外と承認を確かめる通しで、51 GiB の疎ファイルが `SKIPPED_TOO_LARGE` で外れることだけを確認。写しと戻しは行っていない）
2. **合わないのは、診療の途中で再参照する画像、書き換え不能な保存を条文が求める記録、保全の義務が続く資料です。** 診療での再参照なら容量プールか S3 Glacier Instant Retrieval、書き換え不能な保存ならバケット側の機能が前提になります。バケット側の Object Lock は不可逆で、保持期間を名指しした承認が要ります
3. **連携先の多くは、アーカイブ用のバケットにしか届きません。** S3 Inventory、S3 Metadata、S3 Storage Lens、Amazon Macie、AWS Backup は、読んだページに FSx for ONTAP の Access Points の記載がありませんでした。Access Points 側は、イベント通知、`RestoreObject`、バージョニング、Object Lock、ライフサイクルを使えません。元のボリュームの側を見る道具は、ONTAP REST API、NFS、`ListObjectsV2`、Amazon CloudWatch のメトリクスです
4. **表形式のデータ、データベースのファイル、VM のディスクイメージは、ファイル単位で移しません。** 表やアプリケーションのメタデータが元のパスを指し続けるため、ファイルだけを消すと読み取りが失敗します（[ファイル単位で移してはいけないデータ](#ファイル単位で移してはいけないデータ)）
5. **移して得になるかは、単価の差だけでは決まりません。** 1 オブジェクトにつき 40 KB の追加メタデータ、最小保管期間、取り出しとリクエストの料金で、小さなファイルが多いほど差が縮みます（[保管料金の損益分岐の考え方](#保管料金の損益分岐の考え方)）

![構成図。上の枠の AWS Step Functions が、AWS Lambda（5 GiB 以下のハッシュ）、AWS Fargate（5 GiB 超のハッシュとコピー）、Amazon DynamoDB（台帳）、Amazon SNS（承認の依頼）を呼び、承認する人が結果を返す。AWS Step Functions は、Amazon S3 Access Points に CopyObject、DeleteObject、元の HeadObject を呼び、アーカイブ用の汎用バケットにコピー先の HeadObject（照合）を呼ぶ。下の段では、Amazon FSx for NetApp ONTAP のボリュームのファイルが、S3 Access Points からチェックサム付きのサーバー側コピーで、汎用バケット（S3 Glacier Instant Retrieval、Flexible Retrieval、Deep Archive）へ写る。同じリージョンの別のバケットの 2 つ目の写しは、汎用バケットからではなく S3 Access Points から直接作る（経路 C）。移す前のボリュームは AWS Backup でバックアップできる（経路 A）。バケットが S3 Glacier Instant Retrieval のときは、AWS Cloud の内側の AWS Backup と、AWS の外のバックアップ製品（Clumio など）で守れる（経路 B）。選別は Komprise などのデータ管理ソフトに任せられる（経路 D）。戻す流れは図の下の注記にある](../../../../_assets/images/archive-verify-delete.svg)

### 用語と区分の語

この節の表と、後の表で使う語です。

| 語 | 意味 |
|---|---|
| 写して消す流れ | ボリュームのファイルを、Access Points の S3 API だけで S3 Glacier 系のバケットへ写し、チェックサムを照合し、人の承認の後にだけ元を消す流れ。戻すときは、バケットで復元してから Access Points へ写し戻す |
| 流れの 12 段階 | 選ぶ（S1）、記録する（S2）、写す（S3）、照合する（S4）、承認する（S5）、消す（S6）、戻す（S7）、検索する（S8）、保護する（S9）、監査する（S10）、通知する（S11）、費用を報告する（S12） |
| 文書 | AWS またはベンダーの公開ページに、その組み合わせの記載がある |
| 実測 | 実機で確かめた記録がある。出典は、パターンのリポジトリの README、他のリポジトリの記録（リンクを付ける）、またはこの Hub の比較資料 |
| 記載なし | 読んだ範囲に、記載も実測もない。非対応という意味ではない |
| 推測 | 読んだ記述からの推論で、測っていない |
| 容量プール | FSx for ONTAP の、使った量だけ課金される低価格の保管領域。ファイルは元のパスで見えたままになる |
| S3 Glacier Instant Retrieval | S3 Glacier 系のうち、復元なしですぐ読めるクラス |
| 復元が要る 2 クラス | S3 Glacier Flexible Retrieval と S3 Glacier Deep Archive。読む前にバケットで復元が要る |

流れの実装が、冒頭で定義したパターンです。パターンが持つのは S1 から S7 と、S11、S12 の一部（通知と件数のメトリクス）です。S8 から S10 の大半は、利用者が連携先を足します。

### オンプレミスの ONTAP で公開されている階層化とアーカイブの用途

オンプレミスの ONTAP から Amazon S3 へ移す方法の対応表（FabricPool、SnapMirror Cloud、Copy and Sync など）は、[サーバー側コピーのノート](s3-access-points-server-side-copy-use-cases.md#オンプレミスの-ontap-での運用からの置き換え)にあります。ここでは、公開された導入事例と製品文書が、冷えたデータをなぜ、どう移しているかを足します。業界で示し、数値は条件が書かれていないものを転記しません。

| 用途 | 業界 | 移す理由 | 移した後にファイルは見えるか | 取り出しの記述 | 出典 |
|---|---|---|---|---|---|
| FabricPool と StorageGRID で、使われていないブロックを階層化 | 医療・生命科学の非営利の財団 | 高価な記憶域に画像、動画、測定ファイルのすべてを置き続けると容量と予算が逼迫する | 見える。階層化は透過的で、必要になれば自動で性能層へ戻る | 時間の記載なし | N9、N2 |
| FabricPool と StorageGRID で、データを自動階層化 | 大学の宇宙物理の研究所 | 観測データの保管費用を下げる | 見える（FabricPool は透過）。事例は戻し方に触れていない | 記載なし | N10、N2 |
| FabricPool で媒体コンテンツを階層化 | メディア事業者（欧州） | 制作と保管の費用と需要の均衡 | 見える | 記載なし | N11 |
| データ管理ソフトで最終アクセスの分布を測り、冷えたデータを容量ストレージへ | 生命科学企業 | 最終アクセスの分布から、移せる比率を出し、予算要求の根拠にした | 製品の記述は、ユーザーとアプリを止めずに移すとだけ | 記載なし | K2 |
| データ管理ソフトの階層化で、主 NAS の容量を空ける | 製薬企業（匿名） | 非構造データの増加、ハードウェア追加の回避 | 見える。パスを保つと書く | 研究者は変化に気づかないと書く（時間の記載なし） | K3 |
| 自動階層化で NAS のファイルをテープへ | 大学（米国、匿名。ONTAP ではない） | 高速 NAS に数か月から数年読まれないファイルを置くのは高価で、将来のために保持は要る | 見える。テープにしかないファイルは自動でディスクへ戻る | 時間の記載なし | Q1 |
| S3 互換のテープ基盤での長期保存 | 放送事業者（英国。ONTAP ではない） | アナログカセットの置き換え。サイバー攻撃からの隔離 | 見えない。素材管理から検索して取り出す | 制作チームは「ほぼ即時」と書く（ベンダーの事例） | SP1 |
| メタデータカタログとポリシーで、ディレクトリ単位にアーカイブ | 研究機関と大学（ONTAP の記載なし） | 急増するシーケンスデータ。使用率の逼迫 | 研究者のアクセスを保つと書く（要約のみ） | 記載なし | SF1 |
| StorageGRID の Cloud Storage Pools で、S3 Glacier 系などへ移す | 一般（製品文書） | 低頻度のオブジェクトの費用削減 | オブジェクトとして StorageGRID が管理する。FabricPool と同じバケットには使えない | FabricPool の階層先には使えない（取り出しの遅延が理由） | N3 |
| SnapMirror Cloud で、スナップショットをオブジェクトストレージへバックアップ | 一般（製品文書） | 長期保持。旧来のテープバックアップの置き換え | 見えない。復元の操作が要る | 取り出しは S3 の取り出し時間に従う | N4 |

読み取れることは 3 つです。

1. 公開事例の動機は、容量の逼迫と費用です。冷えた比率を最終アクセスで測ってから移す順序（K2、A4）は、流れの S1 に使えます
2. 元のパスで開ける事例（N9、N10、K3、Q1）が大半で、ファイルを消して S3 Glacier Flexible Retrieval と S3 Glacier Deep Archive へ写す ONTAP の公開事例は、読んだ範囲に見つかりませんでした。FabricPool と Cloud Tiering の対象クラスは、この 2 クラスを含まないと書かれています（N1、N6）。パターンの `CopyObject` による書き込みに、公開された先例はありません
3. 数値の多くはベンダーのページの記述で、条件が書かれていません。順序（アーカイブが先、階層化が後）だけを引く方針は、[アーカイブと階層化の順序のノート](../../cost/notes/archiving-and-tiering-are-ordered-not-alternatives.md)と同じです

### FSx for ONTAP の新規の利用者と既存の利用者の用途

「新規」はこれから入れる利用者で、冷えたデータの行き先を選ぶ段階です。「既存」はすでにボリュームを運用していて、容量の逼迫、費用、保持のどれかに向き合う段階です。サーバー側コピーそのものの用途（バケットとボリュームの間の移動、5 GiB 超のコピーなど）は、[新規の利用者と既存の利用者の用途](s3-access-points-server-side-copy-use-cases.md#新規の利用者と既存の利用者の用途)の表にあるので、ここでは繰り返しません。

| 利用者 | 用途 | 公開されている根拠 | 出典 |
|---|---|---|---|
| 新規 | 移行の前に、冷えたデータの比率を測り、SSD 層の大きさを決める | 測り方として、アクセスログ、最終アクセス時刻、アプリの担当者への聞き取り、パイロットを挙げる。ブログは 80 対 20 を例にする | A5 |
| 新規 | 移行中に Cloud Write で、容量プールへ直接書き込む | 匿名の製造業の事例で、300 TB を超える移行が約 2 週間から 2 日になったと書く | A6 |
| 新規 | 移行後に、最終アクセス日で最初のアーカイブを実行する | 匿名の製造業の事例。データ管理ソフトの動的リンクで、FSx for ONTAP と S3 の両方から開ける。取り出しの費用の前提は S3 Glacier Instant Retrieval に月 10 TB | A4、K1 |
| 既存 | 容量プールへの階層化。Auto の冷却期間は既定 31 日（2 から 183 日） | SSD の使用率が 50% 以下では All だけが階層化し、90% 以上で冷たいデータを SSD へ戻さなくなり、98% 以上で階層化が止まる。ファイルのメタデータは SSD に残る | A3 |
| 既存 | All の階層化ポリシー、または cloud retrieval policy の Never | 読まれても SSD へ戻さない。読み取りのたびに容量プールの遅延がかかる | A3 |
| 既存 | S3 Glacier 系への退避 | AWS の発表と対応表は、S3 Glacier 系への退避を用途として挙げていない。Access Points 側は Object Lock、ライフサイクル、バージョニング、`RestoreObject` に非対応と書く。照合、削除、復元の運用は利用者が組む | A1、A2 |

FSx for ONTAP で S3 Glacier 系を行き先に選んだ公開事例は、読んだ範囲では A4 の 1 件（匿名）だけでした。S3 Access Points のサーバー側コピーを移行の段階で使った事例は見つかっていません。

FSx for ONTAP ではない参考事例が 3 つあります。大学が研究室のサーバーのバックアップを S3 Glacier Deep Archive へ置いた事例（A10）、ゲノムのシーケンス出力を 90 日後に S3 Glacier Deep Archive へ移すホワイトペーパー（A8。ページ冒頭に歴史的参照のみと書かれている）、放送アーカイブを S3 Glacier Instant Retrieval と Intelligent-Tiering に置いた事例（A9）です。いずれも S3 を最初から正本にしていて、FSx for ONTAP のボリュームからファイルを消す流れの根拠にはなりません。

### 業界別の用途と、写して消す流れの適合

「適合」の列は、このノートの判断です。公開根拠があるのは、データの種類と取り出しの記述（出典の列）までで、適合の判定は、パターンの性質（元のパスで開けない、戻しに復元が要る、Object Lock を使わない）に照らした推論です。

| 業界 | データ | 読まれにくい理由 | 戻しに待てる時間の目安 | 適合と、合わないときの代替 |
|---|---|---|---|---|
| メディア、映像制作 | 完了した制作物の原版、マスター、素材 | 再利用や再放送まで読まれない。公共放送の事例は 100 年分の保存を目的にする（A9） | 公共放送は S3 Glacier Instant Retrieval で即時に近い取り出し（A9）。S3 Glacier Flexible Retrieval なら迅速 1 から 5 分、標準 3 から 5 時間（A7） | 条件付きで合う。制作の再開に数時間待てる素材が対象。単一ファイルが 50 GiB を超えるマスターや非圧縮の素材は Access Points へ戻せないので、大きさの分布を `ListObjectsV2` の `Size` で先に数える（パターンは 50 GiB 超を選択から外す）。素材管理システムがパスで素材を参照するなら、移動後の所在の更新が要る。フォルダーに小さなファイルが数千ある素材は、状態遷移の数が先に費用を決めうるので、まとめてからアーカイブにする設計も検討する（その場合、照合と戻しの粒度が変わる）。即時性が要るなら S3 Glacier Instant Retrieval か容量プール |
| 生命科学、ゲノム | 生のシーケンサー出力（BCL、FastQ） | 解析後は読まれない | 研究単位で復元を依頼する運用例がある（A8）。S3 Glacier Deep Archive は標準 12 時間以内、大容量 48 時間以内（A7） | 合う。ただし BAM や生データが 50 GiB を超えると、Access Points へ戻せない（A2）。公式ページは、50 GiB の上限をアップロードに対するものとし、それを超えるオブジェクトのダウンロードはできると書く。戻し先が Access Points でなく研究者のホストなら、バケットから `aws s3 cp` で直接取り出せる可能性がある（この手順は通していない）。パターンは、50 GiB 超を選択から外す |
| 医療 | 医用画像（DICOM） | 古い検査はまれにしか読まれない | 診療での再参照は待てない場合が多い（このノートの判断。公開根拠なし） | 合わないことが多い。再参照があるなら容量プールか S3 Glacier Instant Retrieval。画像の長期保管を医用画像の専用サービスに任せる選択肢もある（AWS HealthImaging は長期アーカイブを用途に挙げる。HI1） |
| 金融 | 口座の記録、通信、帳簿 | 規則上の保管のために置く | 規則は迅速に提出できることを前提にする（R6） | 単独では合わない。規則が書き換えと消去のできない形式、または監査証跡を求める（R6）ので、バケット側の Object Lock などが前提になる。パターンは Object Lock を使わない |
| 研究機関、大学 | 研究データ全般 | 公刊後、再現性と監査のためだけに保持する | 要求時に提供できること | 合う。保持が 3 から 10 年以上（下の表）なので、S3 Glacier Deep Archive の最小保管期間 180 日は問題にならない。単一ファイルが 50 GiB を超える画像スタックなどは、上の生命科学の行と同じ扱い。バケット側の S3 Lifecycle で削除の時期を決められる（Access Points 側にライフサイクルはない）。ただし S3 Lifecycle による削除はパターンの承認を通らないので、廃棄の承認は保持期限が来た時点で別に取る。論文やデータ管理計画に書いた保存場所は、移した後は無効になるので、パターンが書く `manifests/<runId>.json` から所在の一覧を作り、計画の記録に添える |
| 航空機製造など | 品質記録（設計データの管理を含む体系） | 製造の適合の証明のために保持する | 記載なし | 条件付き。条文が求めるのは品質記録で、CAD ファイルそのものの保持期間ではない（R5）。小さなファイルが多いと、1 つにつき 40 KB のメタデータ課金が積み上がるので、先に見積もる |
| 法務 | 電子的に保存された情報（訴訟の保全の対象） | 訴訟の予期から保存義務が続く | 要求に応じて提出 | そのままでは合わない。保全の対象を移動と削除から外す仕組みが要る。パターンは、保全の対象のプレフィックスと除外パターンを入力に持ち、一致したファイルを選択から外す。保全の対象の特定は利用者の法務の判断で、パターンはその判断を代替しない。それでも承認の段で、対象が保全の対象でないことを人が確かめる運用は残る。保全中は戻しも止める |
| 公共 | 公文書（PDF、スキャン画像、メール） | 情報公開請求への対応と歴史資料 | 記載なし | 適合は未判断（判断の材料がない）。保存期間の一次資料（米国の記録スケジュール、日本の公文書管理）を読めていない。検索の索引が別に要る |
| 半導体、自動運転、石油ガス | 設計データ、走行ログ、地震探査の生データ | 完了後の再現、検証、再処理 | 記載なし | 適合は未判断（判断の材料がない）。保持期間の公開された一次資料を見つけていない。ファイルの大きさが 50 GiB を超えるもの（生映像、地震探査の生データなど）は Access Points へ戻せない。小さなファイルが多い設計データは課金の見積りを先に |
| 製造業（外観検査の画像、学習データ） | 検査の画像、検査結果、学習データの版 | 再学習で読み返すまで読まれない | 記載なし | 推測。再学習の頻度と、戻しを数時間から 48 時間待てるかで決まる。公開根拠は読んでいない。学習データの版はデータ基盤側の版管理で残し、元の画像だけを移す設計もある |
| 移行後に残った旧環境の資産 | 旧環境のイメージのエクスポート、移行の証跡 | ロールバックの猶予が過ぎると読まれない | 記載なし | 推測。ロールバックの猶予が過ぎた後なら合う。公開根拠は読んでいない。使用中の VM のディスクイメージやデータストアは対象にしない（[ファイル単位で移してはいけないデータ](#ファイル単位で移してはいけないデータ)） |

合わない場合の代替を、見え方の要件で並べ直します。

| 要件 | 選ぶもの | 引き受けること |
|---|---|---|
| 移した後も、元のパスでファイルを開く | 容量プール（Auto、All、cloud retrieval policy の Never） | 保管料金の下げ幅は、容量プールまで（Single-AZ で S3 Standard と同水準）。復元を待つ運用は要らない |
| 元のパスは保ち、ファイルを移す | データ管理ソフト（動的リンクやスタブ） | NFS か SMB でマウントする構成。製品のライセンスが要る |
| 即時に読め、バケット側のバックアップ製品で守る | S3 Glacier Instant Retrieval | 保管料金は復元が要る 2 クラスより高い |
| 書き換え不能な保存、または保全 | バケット側の Object Lock などと、保持期間を名指しした承認 | 不可逆。[不可逆な操作の承認は作業の承認とは別に取る](../../security-governance/notes/irreversible-operations-need-separate-approval.md)を先に読む |
| 数時間から 48 時間待て、元のパスで開く必要がない | 写して消す流れ | スタブも透過な呼び戻しもない。ファイルは利用者のフォルダーから消える |

### ファイル単位で移してはいけないデータ

パターンの選択条件は、更新時刻か最終アクセス時刻、パス、大きさ、除外パターンです。ファイルが開かれているか、そのファイルを別のメタデータが指しているかは判定しません。次のデータは、ファイル単位で移すと、移した後の読み取りが失敗するか、動いているアプリケーションを壊します。

| データ | ファイル単位で移さない理由 | 代わりに | 区分 |
|---|---|---|---|
| Apache Iceberg、Delta、Hive 形式のパーティションで管理された表のデータファイル | 表のメタデータ（マニフェスト、スナップショット、パーティションの定義）が元のパスを指し続ける。ファイルだけを消すと、表を読むクエリが失敗する | 表の側の機能（スナップショットの期限切れ、パーティションの切り離し）で整理し、表から切り離した後のパスだけを対象にする | 推測。一般的な表形式の仕組みからの推論で、各形式の公式ドキュメントは読んでいない |
| データベースのデータファイル、バックアップ中のファイル | 更新時刻が古くても読まれ続けることがある。データベースやアプリケーションが、古いデータの退避や階層化を自分で持つことがある | アプリケーション自身の機能を先に検討する。`prefix` にデータディレクトリを含めない。パターンの除外パターンの既定で外れる（既定には、VM のディスクイメージ、データベースのファイル、表形式のメタデータが入る） | 推測 |
| VM のディスクイメージ（VMDK、VHD、qcow2 など）とデータストアのファイル | 電源が切れていても、更新時刻が古いだけで使用中のことがある。戻したファイルは所有者 0:1 か root:bin、モード 644 になるので、起動側のユーザーが読めない可能性がある。VM のディスクイメージは、パターンの除外パターンの既定にも入る | ボリューム全体の保護は AWS Backup（比較資料の経路 A）。旧環境のイメージは、ロールバックの猶予が過ぎてから別の手順で移す | 推測。戻した後の所有者とモードは実測（下の「実機の通しで確かめた挙動」） |
| 小さなファイルが数百万ある領域 | 1 オブジェクトにつき 40 KB の追加メタデータと、ファイル数に比例する状態遷移の費用が、保管料金の差を打ち消しうる | 日付や装置の単位で tar や zip にまとめてから移す（パターンにまとめる段階はない）。`prefix` を月ごとに分けて実行すると、承認の一覧も小さくなる（試していない運用例） | [保管料金の損益分岐の考え方](#保管料金の損益分岐の考え方)を参照 |

### 保持規則の例

保持の列は、条文や方針に書かれた数字の転記です。**記録の保持規則の例であって、法的な助言ではありません。** 適用される対象は条文の範囲で、データの種類と一致するとは限りません。

| 業界 | 規則 | 書かれていること | 注意 | 出典 |
|---|---|---|---|---|
| 医薬品の治験 | 21 CFR 312.57(c) | スポンサーは、販売承認の後 2 年間（承認されない場合は、治験薬の出荷が止まり FDA に通知した後 2 年間）、この部が求める記録と報告を保持する | 米国の規則 | R7 |
| 医療（米国の病院） | 42 CFR 482.24(b)(1) | メディケアの参加条件として、診療録を少なくとも 5 年保持する。(c)(4)(vi) は記録に含める事項に放射線と検査の報告を挙げる | 画像データそのものが診療録に含まれるかは、読んだ条文に書かれていない。州法の期間と日本の診療録の保存年限は読めていない | R4 |
| 金融（米国の証券会社） | 17 CFR 240.17a-4(c)、(f)(2) | 口座の開設と維持に関する記録は口座の閉鎖から 6 年以上。電子記録は、変更と削除の完全な監査証跡を保つか、書き換えと消去のできない形式で保存する | 読んだのは (c) から (f) の一部で、(a)(b) の期間は読んでいない | R6 |
| 航空機製造 | 14 CFR 21.137(k) | 品質記録を、製造した製品と部品について少なくとも 5 年、重要部品について少なくとも 10 年 | 対象は品質記録で、CAD ファイルではない | R5 |
| 研究費の助成（米国） | 2 CFR 200.334、45 CFR 75.361 | 最終の財務報告の提出から 3 年。訴訟、請求、監査が始まっていれば解決まで | 書面で延長を求められることがある | R2、R3 |
| 研究費の助成（英国の資金提供者） | 大学による要約 | プロジェクト終了後、AHRC は少なくとも 3 年、BBSRC は最低 10 年、CRUK は少なくとも 5 年、EPSRC は 10 年（最後の請求またはアクセスから）、MRC は基礎研究で 10 年以上、集団保健と縦断研究で 20 年。NIH と STFC は期間の指定なし | 二次資料。資金提供者の一次ページは読めていない | R9 |
| 訴訟 | FRCP 37(e) | 訴訟の予期または進行中に保存すべき電子情報が、合理的な措置を怠って失われ、復元も代替もできないとき、裁判所は措置を命じる | 固定の保持期間はなく、事案ごと | R8 |
| 医療情報の安全管理（米国） | 45 CFR 164.316(b)(2)(i) | 方針と手順などの文書を、作成日か有効だった最後の日の遅い方から 6 年保持する | 患者の記録ではなく、文書化の保持。台帳がこの文書に当たるかは判断していない | R1 |

### 実機の通しで確かめた挙動

パターンを、FSx for ONTAP の 1 つのファイルシステムで 3 つの確認を行いました（2026-11-26、ap-northeast-1、第 1 世代 `SINGLE_AZ_1`、ONTAP 9.19.1P4D1、UNIX スタイルのボリューム、S3 Glacier Flexible Retrieval、各手順 1 回）。「5.5 GiB を含む 7 ファイルの通し」、11 ファイルを作って 4 ファイルが選ばれた「除外と承認を確かめる通し」、256 KiB のファイル 8 つで承認の結び付けを確かめた「直接呼び出しを確かめる確認」です。用途の判断に効く事実を、どの確認の値かを付けて挙げます。環境と手順ごとの結果は、[比較資料の節](../../../reference/comparison/archive-tiering-library-options.md#実機での通しの結果)に、デプロイと運用の前提条件は[同じ資料の節](../../../reference/comparison/archive-tiering-library-options.md#デプロイと運用の前提条件)にあります。記録の原本は、パターンの `solutions/data-lifecycle/archive-verify-delete/README.md` にあります。

| 用途の判断に効く事実 | 結果 |
|---|---|
| 戻しの時間（5.5 GiB を含む 7 ファイルの通し） | 取り出しの種類を Expedited にして、5.5 GiB を含む 6 ファイルを 287 秒で戻し、SHA-256 は全件、事前に NFS で記録した値と一致した。Standard と Bulk の完了待ちは測っていない |
| 戻しと戻した後の照合（除外と承認を確かめる通し） | 小さい 3 ファイルを Expedited で 192 秒で戻し（ポーリング間隔は 1 分に設定）、戻した後の再ハッシュで 3 件が `RESTORE_VERIFIED` になった。NFS の SHA-256 も、手順の前の値と一致した。5 GiB を超えるファイルの戻した後の照合（Fargate の経路）は、この通しでは通っていない |
| 戻した後の属性 | 所有者 0:1（5.5 GiB を含む 7 ファイルの通し）か root:bin（除外と承認を確かめる通し）、モード 644、更新時刻は戻した時刻。5.5 GiB を含む 7 ファイルの通しは、生成された再付与スクリプトを root で実行すると、元の uid、gid、mode、mtime に戻った。除外と承認を確かめる通しはスクリプトの生成までで、`RESTORE_VERIFIED` の 3 件分が出た |
| 承認の拒否（5.5 GiB を含む 7 ファイルの通し） | 拒否すると何も消えなかった |
| 起動者と同じ申告の承認、直接の削除（除外と承認を確かめる通し） | どちらも拒否され、ファイルは残った。承認者を別の ARN で申告すると受理された（申告値の比較。2 つ目の主体は用意していない） |
| 直接呼び出しと承認の結び付け（直接呼び出しを確かめる確認） | 別の実行の ARN、文字列 `manual`、削除済みの `approvedBy` を付けた入力のどれでも `NOT_APPROVED` で、止めた実行の `APPROVED` の項目は消えなかった。止めた実行自身の ARN を `claim` にした呼び出しも、`claiming execution is not running` で拒否された。承認の期間（`ApprovalValidityHours`）の超過は実機では確認しておらず、単体テストだけ |
| 承認を待つ間の書き換え（5.5 GiB を含む 7 ファイルの通しと除外と承認を確かめる通し） | 同じ大きさのまま mtime が更新された書き換えは検出され、そのファイルは消えず `CHANGED` で残った |
| 除外（除外と承認を確かめる通し） | `*.vmdk`、保全用のプレフィックス、最小サイズ未満（131,071 B）は選ばれず、131,073 B と 1 MiB は選ばれた。51 GiB の疎ファイルは `SKIPPED_TOO_LARGE` で外れ、写しも戻しもしていない |
| 同じ実行 ID の再利用、削除の再試行（除外と承認を確かめる通し） | 再利用は `InvalidInput` で拒否された。削除の再試行と再開は単体テストだけで、実機では通していない |
| 通知とアラーム（除外と承認を確かめる通し） | 失敗の通知は、カスタマー管理キーで暗号化した SNS トピックから届いた。アラームは 6 個あり、手で ALARM にした 1 個は通知を発行できた。滞留のアラームは、メトリクスの存在までで、ALARM になるまでは待っていない |
| 最後のファイルを消したとき（5.5 GiB を含む 7 ファイルの通し） | 空になった親ディレクトリも消えた。戻しの `CopyObject` が親ディレクトリを作り直す |
| 最終アクセス日で選ぶとき（5.5 GiB を含む 7 ファイルの通し） | ハッシュ計算の読み取りがファイルの atime を実行時刻に更新する。dry run の直後に同じ入力で本番を回すと、0 件で終わった |

確認の規模は、5.5 GiB を含む 7 ファイルの通しが 7 ファイル、除外と承認を確かめる通しが選ばれた 4 ファイル、直接呼び出しを確かめる確認が 8 ファイルで、多数のファイルでの所要時間と費用は測っていません。

### 消した結果が及ぶ範囲

Access Points 経由でファイルを消すと、ボリュームの外の仕組みにも影響が及びます。測ったのはボリュームの使用量だけで、ほかは確かめていません。

| 仕組み | 消した後に起きること | 区分 |
|---|---|---|
| ボリュームのスナップショット | ファイルを消しても、使用量は約 800 MiB しか減らなかった。スナップショットの使用量が 224 MiB から 1,253 MiB に増え、そのスナップショットを消すと使用量は元の水準に戻った（ランダムデータの 1 GiB、ストレージ効率化ありのボリューム、1 回） | 実測（[比較資料](../../../reference/comparison/archive-tiering-library-options.md#部品ごとに確かめたこと)） |
| スナップショットからの復元 | 消したファイルがスナップショットに残るので、そこから戻せる可能性がある。Access Points 経由で消した後に、スナップショットからファイルを戻せるかは試していない | 推測 |
| SnapMirror の宛先 | 転送はスナップショットの単位なので、次の更新で削除が宛先に伝わると考えられる。宛先側の古いスナップショットには残る。測っていない | 推測 |
| AWS Backup（ボリューム） | ボリューム単位のバックアップが消す前の安全網になる。戻すのはボリューム単位で、戻し先は新しいボリューム | 文書（A2 と同じ FSx for ONTAP のユーザーガイドのバックアップの節） |

既存のスナップショットポリシーと SnapMirror 関係があるボリュームでは、パターンを回す前に、検証用のボリュームで「消す、スナップショットから戻せるか、宛先に何が出るか」を 1 回ずつ確かめます。スナップショットの保持期間は、ボリュームの容量が戻る時期を決めます。

### 保管料金の損益分岐の考え方

S3 Glacier 系のクラスは、1 GB あたりの保管単価が容量プールより低くても、移した結果の月額が下がるとは限りません。次の要素が、移したファイルの数と大きさと戻す頻度で効きます。クラスごとの記載は [Comparing the Amazon S3 storage classes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/storage-class-intro.html)（2026-11-26 閲覧）です。単価は [Amazon S3 の料金ページ](https://aws.amazon.com/s3/pricing/)か Pricing API で、取得日とリージョンを付けて取ります。このノートはアーカイブ用クラスの単価を載せません。

| 要素 | 記載 | 効く条件 |
|---|---|---|
| 1 オブジェクトの追加メタデータ | S3 Glacier Flexible Retrieval と S3 Glacier Deep Archive は、1 オブジェクトにつき 40 KB（32 KB はそのクラスの単価、8 KB は S3 Standard の単価）。S3 Glacier Instant Retrieval は最小の課金対象サイズが 128 KB | 小さなファイルが多いほど、保管量に対する比率が上がる。1 MiB のファイルなら 40 KB は約 3.9%（40 ÷ 1,024 の計算） |
| 最小保管期間 | S3 Glacier Instant Retrieval と S3 Glacier Flexible Retrieval が 90 日、S3 Glacier Deep Archive が 180 日 | それより短い期間で削除や上書きをした場合の課金の扱いは、料金ページで確認する（このノートでは確認していない） |
| 取り出しの料金 | 3 クラスとも GB あたりの取り出し料金がかかる | 戻す頻度と量が増えるほど効く。取り出しの種類（迅速、標準、大容量）で単価が違う |
| リクエストの料金 | 書き込み（`CopyObject`）と復元のリクエストに、リクエスト数あたりの料金がかかる（単価は料金ページ） | ファイル数に比例する |
| 2 つ目の写し | 別のバケットの保管料金（比較資料の経路 C） | 復元が要る 2 クラスでバックアップ製品が使えないとき、常に加わる |
| ワークフローの状態遷移 | パターンの README の使用量の表では、5.5 GiB を含む 7 ファイルの通しが dry run 119 遷移、本番 127 遷移、6 ファイルの戻し 107 遷移で、1 ファイルあたり約 17 から 18。除外と承認を確かめる通し（選ばれた 4 ファイル、小さいファイルのみ）が dry run 72（18）、承認の拒否 73（18.25）、3 削除と 1 `CHANGED` の本番 78（19.5）、戻し 56（14）。ファイルの状態と経路で 1 ファイルあたり 14 から 19.5 遷移（親と子の実行の合計を割った値。1 回ずつの実測） | ファイル数に比例する。単価は確認していない |
| 容量プールに残るスナップショット | スナップショットが残る間は、消しても使用量が下がらない | 既存のスナップショットポリシーの保持期間 |

保管料金だけを見た 1 か月の差額は、次の式で見積もります。P は GB あたり月の単価で、KB は GB に直して計算します。

> 差額 ＝ 移した GB × （P容量プール − Pアーカイブ） − 移したファイル数 × （8 KB × PS3 Standard ＋ 32 KB × Pアーカイブ） − 2 つ目の写しの保管料金

ここから取り出し、リクエスト、状態遷移の料金を回数に応じて引きます。ファイルの平均の大きさ S（KB）で見ると、保管料金だけで差額が 0 になる大きさは次のとおりです。S がこれより小さいファイルを移すと、保管料金の差額が負になります。

> S ＝ （8 KB × PS3 Standard ＋ 32 KB × Pアーカイブ） ÷ （P容量プール − Pアーカイブ）

東京リージョンの容量プール（Single-AZ）は $0.0238 / GB-月、S3 Standard は $0.025 / GB-月です（2026-11-24 取得）。式に入れるアーカイブ用クラスの単価は、料金ページから取得日を付けて代入してください。この式は保管料金だけを見ています。SSD 層の確保容量が減らなければ SSD の料金は下がらず、移した効果は出ません（[容量プールの比較](../../../reference/comparison/tiering-policies.md)）。

### 連携先と流れの段階の対応

連携先を、流れのどの段階に置くかと、FSx for ONTAP の S3 Access Points まで届くのか、アーカイブ用のバケットにしか届かないのかで整理します。まず段階ごとの標準の構成を示し、その後に連携先を種類別に並べます。

#### 流れの段階と標準の連携先

| 段階 | パターンが持つもの | 追加で組み合わせる連携先 |
|---|---|---|
| S1 選ぶ | `ListObjectsV2` の更新時刻、または ONTAP REST API の最終アクセス時刻 | Amazon EventBridge Scheduler（定期起動）、Amazon Macie か Amazon Comprehend などによる分類（移す前に限る） |
| S2 記録 | Amazon DynamoDB の台帳（大きさ、ETag、SHA-256、CRC64NVME、所有者、モード、時刻） | なし |
| S3 写す | AWS Step Functions の `copyObject`、5 GiB 超は AWS Fargate のマルチパートコピー | S3 Batch Operations（実装案として並ぶ） |
| S4 照合 | バケットの `HeadObject` のチェックサムと台帳の比較 | なし |
| S5 承認 | `waitForTaskToken`、Amazon SNS の通知、AWS Systems Manager Parameter Store のトークン | Amazon Q Developer in chat applications、Slack、Microsoft Teams、チケットシステム |

| S10 監査 | 台帳の `deletedBy`、Step Functions の実行履歴 | AWS CloudTrail のデータイベント、S3 Metadata |

### 自環境での始め方

検討、検証、構築、運用の順に、何を決めるかです。

| 段階 | 決めること | 判断の材料 |
|---|---|---|
| 検討 | 冷えたデータの比率と読まれ方を測る | アクセスログ、最終アクセス時刻、アプリの担当者への聞き取り、パイロット（A5）。最終アクセス時刻で選ぶ場合は、パターン自身の読み取りで atime が更新されるので、dry run の直後に本番を回さない |
| 検討 | 移した後も元のパスで開く必要があるか | ある: 容量プール（Auto、All）かデータ管理ソフト。ない: 次へ。[比較資料の選び方](../../../reference/comparison/archive-tiering-library-options.md#選び方)の 1 番 |
| 検討 | 戻しに何時間待てるか | S3 Glacier Instant Retrieval は復元不要。Flexible Retrieval は迅速 1 から 5 分、標準 3 から 5 時間、大容量 5 から 12 時間。Deep Archive は標準 12 時間以内、大容量 48 時間以内（A7） |
| 検討 | 保持、不変性、保全の要件を聞き取る | 要件が書き換え不能な保存や保全の対象を含むなら、このパターンだけでは足りない。バケット側の Object Lock は不可逆で、保持期間を名指しした承認が要る |
| 検討 | ファイルの大きさと数を確認する | 5 GiB 超は Fargate、50 GiB 超は Access Points へ戻せない（A2。パターンは選択から外す）。小さなファイルが多いと、1 つにつき 40 KB のメタデータ課金と最小保管期間が効く（[損益分岐](#保管料金の損益分岐の考え方)）。パスが「装置 / 年 / 月 / 日」なら、`prefix` を月ごとに分けて実行すると承認の一覧が小さくなる（試していない運用例） |
| 検討 | 本番に進める条件を決める | 技術の条件（全件照合、拒否で何も消えない、戻して一致）に加えて、移した後の月額の見込みが運用の工数を上回るか、戻しの申請の入口と応答の目標時間が決まっているか、利用者への案内が済んでいるか。判断する役割（データの持ち主、承認する人、運用の持ち主）を先に決める |
| 検討 | 既存のスナップショットと SnapMirror を確認する | 消した結果が及ぶ範囲を、検証用のボリュームで 1 回確かめる（[消した結果が及ぶ範囲](#消した結果が及ぶ範囲)） |
| 検証 | 部品が自環境で動くか | `CopyObject` のチェックサム、ETag の挙動、`DeleteObject` の `NotImplemented`、スナップショットがある間の容量の挙動を、[比較資料の部品の確認](../../../reference/comparison/archive-tiering-library-options.md#部品ごとに確かめたこと)と同じ手順で 1 回ずつ確かめる |
| 検証 | 最終アクセス時刻で選ぶなら、ONTAP REST API に届くか確かめる | 選ぶ段階は VPC 内の Lambda から ONTAP REST API を呼ぶ（ONTAP の認証情報と管理エンドポイントへの到達性が要る）。NFS のマウントは選ぶ段階では使わない。戻した後の属性の付け直しだけが NFS のホストを要する |
| 検証 | dry run を、小さな `maxFiles` で回す | dry run でもコピーは行われ、アーカイブ用のクラスの保管料金がかかる。削除は行われない |
| 検証 | 承認の拒否、承認待ちの間の書き換え、1 ファイルの戻しを 1 回ずつ通す | 拒否すると何も消えないこと、書き換えたファイルが消えないこと、戻したファイルの SHA-256 が一致することを確かめる |
| 構築 | パターンをデプロイする | [archive-verify-delete](https://github.com/Yoshiki0705/FSx-for-ONTAP-S3AccessPoints-Serverless-Patterns/tree/main/solutions/data-lifecycle/archive-verify-delete) の README の手順 |
| 構築 | アーカイブ用のバケットを設計する | 暗号化、アクセス制御、Block Public Access、S3 Lifecycle による削除の時期、同一リージョンの 2 つ目の写し、CloudTrail のデータイベント、SCP。台帳とマニフェストにはファイルのパスが入る。パスに個人や案件を識別できる名前が含まれる場合は、元のデータと同じ分類で扱う |
| 構築 | 承認できる主体を決める | 開始入力の `requestedBy` と承認の `approver` は呼び出し側が書く申告値で、パターンの分離の検査は、この 2 つの文字列の比較です。主体の証明ではなく、別の ARN を申告すれば受理されます（除外と承認を確かめる通しで確かめた）。実際に承認した主体は、CloudTrail の `SendTaskSuccess` のイベントの `userIdentity` で後から確かめます。承認は台帳に記録され、削除は同じ実行で承認された項目だけを、承認から `ApprovalValidityHours`（既定 24 時間）以内に消します（別の実行の ARN と、止めた実行自身の ARN での直接呼び出しの拒否は実機で確認。期間の超過は単体テストのみ）。起動者と承認者を主体の単位で分けるには、起動と承認の IAM ロールを分ける設計を、利用者が行います |
| 構築 | 消す前に、AWS Backup でボリュームをバックアップする | 戻すのはボリューム単位で、戻し先は新しいボリューム |
| 運用 | 台帳を守る | 台帳が戻しの索引になる。パターンの DynamoDB には point-in-time recovery を設定している。パターンは失敗と滞留のアラームを持つ。通知の購読は、メールの確認を済ませるまで有効にならない |
| 運用 | 戻しの訓練をする | 戻した後は、所有者 0:1、モード 644、更新時刻は戻した時刻になる。再付与スクリプトを root で実行する手順を訓練する |
| 運用 | 費用を突き合わせる | Cost and Usage Report 2.0 と台帳、パターンのメトリクスを突き合わせる |
| 運用 | 利用者に案内する | 移したファイルは利用者のフォルダーから消える。戻しの申請の入口（ファイルポータルなど）を用意する。ファイルポータルのアーカイブの一覧と戻しの申請は未実装 |

#### PoC の計画の雛形

上の表の「検証」を、判断に使える計画にするための雛形です。**雛形であって、数値はこのノートでは決めません。** 空欄と「（決める）」は、利用者が自分のデータと体制で埋めます。成功の基準に書いた条件は、パターンの動作から導いたもので、目標値は利用者が置きます。パターンの README は、この計画の置き場としてこの表へリンクします。

| 確かめる問い | 成功の基準 | 使うデータ | 期間の目安 | Go/No-Go の判断 |
|---|---|---|---|---|
| 選ぶ条件と除外は意図どおりか | dry run で、保全の対象、データベースのファイル、VM のディスクイメージ、表形式のデータが選ばれない。除外の件数が想定と合う | 代表的なフォルダー 1 つ分（`maxFiles` を小さく）。除外すべきものを意図的に混ぜる | （決める） | 除外すべきファイルが選ばれたら No-Go。除外の設定を直して、やり直す |
| 照合は全件で一致するか | 選ばれた全件が `VERIFIED` になる。`MISMATCH` が出たら原因を説明できる | 小さいファイルと、扱うなら 5 GiB を超えるファイル | （決める） | 原因を説明できない不一致があれば No-Go |
| 1 ファイルあたりの遷移数と所要は安定するか | `maxFiles` を段階的に増やしても、1 ファイルあたりの状態遷移数と Fargate の秒数が安定する（このノートの値は、5.5 GiB を含む 7 ファイルの通しが 17 から 18、除外と承認を確かめる通しが 14 から 19.5） | 大きさの分布が本番に近い抜き取り | （決める） | 損益分岐の式が、移す価値を示さなければ No-Go |
| 承認の検査は意図どおりに働くか | 起動者と同じ申告の承認が拒否される。承認を経ない削除が拒否される。承認待ちの間に書き換えたファイルが `CHANGED` で残る | 検証用のファイル | （決める） | 拒否されるべき操作が通れば No-Go |
| 実際に承認した主体を、後から確かめられるか | CloudTrail で `SendTaskSuccess` と削除の記録を引ける。データイベントの記録は、このノートでは未確認 | 検証用の実行 | （決める） | 追えなければ、承認の体制の見直しが先 |
| 戻しは待てる時間に収まり、戻したファイルは使えるか | 戻した後の再ハッシュが `RESTORE_VERIFIED` になる。再付与した後に、取り込みの処理が動く | 実際に戻す用途のファイル。使う予定の取り出しの種類 | 待てる時間の上限は利用者が決める | 待てる時間に収まらなければ、クラスを見直す |
| 運用の体制は決まっているか | 承認する人、戻しの申請の入口と応答の目標時間、利用者への案内、保全の対象を特定する役割が決まっている | （データは不要） | （決める） | 未決なら No-Go |

### よくある誤解

| 誤解 | 実際 |
|---|---|
| 読まれないファイルは、S3 Glacier 系へ移さないと安くならない | 容量プールへの階層化で、Single-AZ では S3 Standard と同水準の単価になる。S3 Glacier 系は、それより下げたい場合や、バケット側の機能が要る場合に選ぶ |
| 連携したい AWS サービスは、Access Points にもバケットにも同じようにつながる | 読んだページに Access Points の記載がないものが多い。バケット側にだけ届く連携は、移した後のファイルが対象になる |
| Amazon Macie で、アーカイブ用のバケットの機密データを後から検出できる | S3 Glacier Deep Archive は対象外と明記されている。移す前に分類するか、Standard のバケットを経由する（後者は試していない） |
| 保持期間が条文にあるので、そのファイルを S3 Glacier 系へ移せば足りる | 条文の期間は記録に付くもので、ファイルの種類には付かない。書き換え不能な保存を求める条文には、移すだけでは足りない |
| アーカイブ用のバケットは AWS Backup で守れる | 復元が要る 2 クラスのオブジェクトは対象外と書かれている。2 つ目の写しを自分で作る |
| 承認があれば、承認者が誰かも台帳で確かめられる | 台帳の `deletedBy` は申告値で、起動者と承認者を分ける検査も、2 つの申告値の比較。実際に承認した主体は CloudTrail の `SendTaskSuccess` のイベントで確かめる |
| 承認があれば、動いているデータベースや表形式のデータも移してよい | 承認の一覧を人が見て、データベースのファイルや表のデータファイルだと気づける保証はない。ファイル単位で移さない理由は[ファイル単位で移してはいけないデータ](#ファイル単位で移してはいけないデータ)にある |
| 消したファイルはスナップショットから戻せるので、容量もすぐ戻る | 消したファイルはスナップショットに残るので、使用量はスナップショットが消えるまで下がらない（実測、1 回）。SnapMirror の宛先への伝わり方は確かめていない |
| 公開事例があるので、同じ用途で動く | ONTAP の公開事例の多くは、元のパスで開ける階層化で、この流れとは別の層。S3 Glacier Flexible Retrieval と S3 Glacier Deep Archive へ写して消す ONTAP の事例は、読んだ範囲に見つからなかった |

### 確認できていないこと

- ONTAP の公開事例で、復元が要る 2 クラスへファイルを写して消す事例の有無。見つからなかったことは、存在しないことの証明ではない
- 多数のファイルでの所要時間と費用、Standard と Bulk の復元の完了待ち、NTFS ボリューム、第 2 世代、Multi-AZ での動作
- 50 GiB を超えるファイルの写しと、バケットからの直接のダウンロード（実測は 5.5 GiB まで。51 GiB の疎ファイルが選択から外れることだけを除外と承認を確かめる通しで確認）
- 5 GiB を超えるファイルの戻した後の照合（Fargate の経路）。除外と承認を確かめる通しは最大 1 MiB で通っていない
- 削除の再試行と再開の実機での通し（単体テストのみ）と、承認の期間の超過、ウォッチドッグが古いトークンを消す動作
- 2 つ目の主体による承認（除外と承認を確かめる通しは同じ SSO の主体が別の ARN を申告した）、滞留のアラームが ALARM になるまでの待ち、Standard と Bulk の戻し
- Access Points 経由で消した後のスナップショットからの復元と、SnapMirror の宛先の状態
- アーカイブ用クラスの最小保管期間より短く削除や上書きをした場合の課金の扱い
- 日本の診療録の保存年限、日本の公文書の保存期間、米国の一般記録スケジュール。条文のページは取得できたが、該当の記述を抽出できなかった
- 半導体の設計データ、自動運転のログ、地震探査の生データの保持期間。公開された一次資料を見つけていない
- 金融の規則の (a)(b) の期間、研究資金提供者の一次ページ。大学の要約（二次）に頼っている
- ServiceNow、Splunk、Datadog のページ。本文が取れないか、HTTP 403 だった
- アプリケーションの製品（文書管理、素材管理、医用画像の保管、研究室の情報管理、設計データの版管理）。種類としての推測で、製品ページは読んでいない
- Amazon Comprehend と Amazon Bedrock の非同期ジョブが、FSx for ONTAP の Access Points のエイリアスを入力に指せるか
- S3 Metadata のジャーナル表が、復元の要求と完了を記録するか
- CloudTrail のデータイベントで、FSx for ONTAP の Access Points の削除がどういうイベントで出るか
- AWS Elemental MediaConvert、AWS Deadline Cloud、AWS Storage Gateway、AWS HealthOmics が、復元が要る 2 クラスのオブジェクトを入力にしたときの動作
- NetApp のページのうち、HTTP 403 で取得できなかったもの（導入事例の一部とブログ）。PDF の事例資料は題名と URL だけを確認し、内容を引いていない
