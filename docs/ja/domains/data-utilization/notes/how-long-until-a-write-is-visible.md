# 書いた側と読む側が違うと、見えるまでの時間は方向で決まる

[🏠 リポジトリトップ](../../../../../README.md) | [Domain — データ活用](../README.md)

---

## 結論

**S3 API で書いてファイルで読む経路と、ファイルで書いて S3 API で読む経路は、同じ構成でも見えるまでの時間が違います。** Amazon FSx for NetApp ONTAP では 4 方向すべてが 1 桁から数十 ms に収まり、**遅い側は「ファイルに書いて S3 で読む」の p50 44 ms** です。

**この差が設計を決めるのは、待ち時間そのものではなく、待つ主体がどちらかだからです。** 収集を S3 で受けて利用をファイル側で行う経路なら 3〜8 ms 側に乗ります。逆に、ファイル側のアプリが書いたものを S3 API のジョブが拾う経路は、**書き込み完了とオブジェクトの出現が同時ではない**ことを前提に組む必要があります。

**同じ 4 方向を Amazon S3 Files で測った記録があり、桁が違います。** 「ファイルに書いて S3 で読む」は p50 63,769 ms（約 64 秒）です。どちらを採るかは反映速度だけで決まりませんが、**この方向がクリティカルパス上にあるかどうかは先に判定してください。**

---

## 4 方向の実測値

出どころは [全方向の可視性比較](https://github.com/Yoshiki0705/S3-Burst-on-ONTAP-Files/blob/main/docs/ja/verification/cross-protocol-directions.md)（2026-08-09、`n=30`）です。

| # | 方向 | p50 | p90 | max |
|---|---|---|---|---|
| 1 | NFS 書き込み（Origin）→ S3 AP `GetObject` | **44 ms** | 49 ms | 328 ms |
| 2 | NFS 書き込み（Origin）→ FlexCache の NFS 読み取り | **6 ms** | 7 ms | 25 ms |
| 3 | S3 AP `PutObject` → FlexCache の NFS 読み取り | **8 ms** | 9 ms | 19 ms |
| 4 | S3 AP `PutObject` → Origin の NFS 直接読み取り | **3 ms** | 5 ms | 8 ms |

**測定条件（全方向共通）**: ap-northeast-1、ONTAP 9.18.1P3D1（両クラスタ）、`SINGLE_AZ_1` / 128 MBps ×2、Origin と Cache は同一リージョンの VPC ピアリング、NFSv3、`actimeo=0`、オブジェクトサイズ 64 B、並列度 1、boto3 の持続セッション、書き込みと読み取りは同一ホスト・単一クロック。

この表から読めることが 3 つあります。

- **方向 3 と 4 の差 +5 ms が FlexCache の加算分です。** Cache を挟むこと自体の費用がこの 5 ms で、経路の他の要素とは分離されています。
- **方向 2 が方向 3 より速いのは、NFS 書き込みが Origin のファイルシステムに直接コミットされ、S3 API のオーバーヘッドを通らないためです。**
- **方向 1 が最も遅く、支配しているのは S3 AP 側の読み出し処理です。** ストレージへの反映が遅いのではありません。

> **64 B・並列度 1 の値です。** 反映の待ち時間を測った測定で、スループットの測定ではありません。**大きいオブジェクトや並列度を上げた場合の値ではないので、そのまま外挿しないでください。**

---

## 引用してはいけない 1 つの値

**同じ方向 1 について、先行する記録には p50 873 ms という値があり、これは引用できません。**

出どころの記録が自分で訂正しています。873 ms は `aws s3api get-object` を毎回起動して測ったもので、**プロセス起動と TLS ハンドシェイクが毎回含まれています。** boto3 の持続セッションで測り直した値が 44 ms です。

**つまり 873 ms の大部分はクライアント側のコストで、ストレージの反映遅延ではありません。** 引用すると、測定手法の費用を製品の特性として設計に持ち込むことになります。

> **一般化できる形**: 反映速度を CLI の 1 回起動で測ると、測っているのは起動コストです。**この構成では 20 倍の差が付きました。** 自分で測るときも、持続セッションか使い捨てプロセスかを条件に書いてください。

## 読み手のマウントオプションが決める観測値

**同じファイルシステム・同じ操作でも、NFS クライアントのマウントオプションで観測値が 300 倍変わります。**

S3 の `DeleteObject` が NFS 側から消えるまでの時間（[同一ボリュームの検証記録](https://github.com/Yoshiki0705/S3-Burst-on-ONTAP-Files/blob/main/docs/ja/verification/s3ap-nfs-visibility.md)、2026-08-09、同リージョン、`SINGLE_AZ_1` / 128 MBps、NFSv3）:

| マウントオプション | 所要 |
|---|---|
| `actimeo=0` | **7 ms** |
| 既定（`acdirmin=30` / `acdirmax=60`） | **2,171 ms** |

**上の 4 方向の表が `actimeo=0` なのはこのためです。** サーバ側の反映を測るために、クライアントのキャッシュ期限を外しています。

**設計上の帰結は 2 つあり、向きが逆です。**

- **「反映が遅い」という観測は、まずクライアント設定を疑ってください。** ストレージ側の値ではないことがあります。
- **逆に `actimeo=0` を本番の既定にはしないでください。** これは測定用の設定で、属性キャッシュを捨てるとメタデータ操作が増えます。**本番で必要なのは、業務が許容できる反映遅延を決めて、それに合う `acdirmin` / `acdirmax` を選ぶことです。**

## マルチパートアップロードの途中が見えないこと

**`CompleteMultipartUpload` の前に、部分的なオブジェクトはファイル側に現れません。** 同一ボリュームの記録で確認されており、Amazon S3 Files でも同じ挙動です（パート 1 の 20 秒後に 3/3 見えず、`CompleteMultipartUpload` 後に 3/3 見える）。

**これは安全側の挙動で、ファイル側のコンシューマが中途半端な内容を読む経路がないという意味です。** 逆に言えば、**大きいオブジェクトの可視性は転送時間ではなく完了時刻で決まります。**

---

## Amazon S3 Files との差

**同一手法（boto3 の持続セッション、64 B、並列度 1、`n=30`）で測った記録があります**（[S3 Files 実測記録](https://github.com/Yoshiki0705/S3-Burst-on-ONTAP-Files/blob/main/docs/ja/verification/s3files-measured.md)、2026-09-01、ap-northeast-1、NFSv4.2、アクセスポイント経由、`actimeo=0`）。

| 方向 | FSx for ONTAP S3 AP | Amazon S3 Files |
|---|---|---|
| S3 に書く → ファイルで読む | 3 ms（方向 4） | **1,533 ms** |
| ファイルに書く → S3 で読む | 44 ms（方向 1） | **63,769 ms** |
| マウント内で書く → 読む | 測定対象外 | 10.7 ms |

**削除と上書きも同じ桁です。** S3 Files 側で、削除は 1,524.9 ms / 64,941.5 ms、上書きは 1,632.1 ms / 64,975.9 ms（`n=10`、タイムアウト 0 件）。**片方向だけが遅いのではなく、ファイル → S3 の向きが一貫して 60 秒級です。**

> **この表で比べているのは反映の待ち時間だけです。** 可用性・運用の手間・費用・プロトコルの可否は別の軸で、ここでは測っていません。**S3 Files の記録は「マウントオプションは揃わない」と明記しているので、上の表は方向ごとの桁の比較として読み、同一条件の対照としては読まないでください。**

**選び方に効くのは、どちらの方向がクリティカルパスに乗るかです。**

| 経路の形 | 効いてくる方向 |
|---|---|
| S3 API で収集し、ファイル側のアプリが利用する | S3 → ファイル。**両方とも秒未満か秒台** |
| ファイル側のアプリが出力し、S3 API のジョブが拾う | ファイル → S3。**ここで桁が分かれます** |
| ファイル側だけで完結し、S3 は別系統の読み取り専用 | 反映速度は設計の制約になりません |

## この数値の範囲外

**未測定・未確認のまま残っている前提を明示します。** これらを埋めた値としてこの節を引用しないでください。

| 前提 | 状態 |
|---|---|
| 大きいオブジェクト・高い並列度での反映速度 | **未測定。** 上の値は 64 B・並列度 1 |
| SMB 側から書いた場合の方向 | 出どころの記録に SMB の測定はありますが（`smbclient` の毎回セッション確立で p50 43 ms）、**手法が違うので上の表と並べられません** |
| Origin と Cache が別リージョン・オンプレミスの場合 | **未測定。** 上は同一リージョンの VPC ピアリング |
| ONTAP の版差 | **未測定。** 9.18.1P3D1 の 1 点のみ |
| 反映遅延の上限に対する保証 | **ありません。** p50 と p90 の実測であって SLA ではありません |
