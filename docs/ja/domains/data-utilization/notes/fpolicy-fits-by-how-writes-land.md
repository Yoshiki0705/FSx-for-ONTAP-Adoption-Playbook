# FPolicy が適合するかは、データをどう読むかではなく、どう書くかで決まる

[🏠 リポジトリトップ](../../../../../README.md) | [Domain — データ活用](../README.md)

---

## 結論

**FPolicy をイベントソースとして使えるかは、データを何で読むかではなく、書き込みがどのプロトコルで着地するかで決まります。**

| 書き込みの着地経路 | FPolicy | 欠落したときの見え方 |
|---|---|---|
| **NFS / SMB** | **動きます。** サブ秒で通知が届き、`mandatory` なら遮断もできます | 通知が途切れたことは KeepAlive の断で分かります |
| **S3 Access Point 経由** | **不発です。** `s3` は event の protocol として存在せず、`mandatory` でも遮断されません | **不発を報告するものがありません。** 静かにゼロ件になります |

読む側は判定に入りません。**同じボリュームを Athena や Spark から S3 Access Point で読んでいても、書き込みが NFS / SMB で着地していれば FPolicy は発火します。** 逆に、読む側がファイルプロトコルでも、書き込みが S3 Access Point 経由なら発火しません。

**そして欠落の意味は用途で違います。** 監視にとって再起動時の欠落窓はログの穴ですが、取り込みにとっては**読み込まれないファイル**です。監視は後から気づけますが、取り込みは気づく契機がありません。

> **Evidence**: `documented` — **著者が別プロジェクトで実測した記録の転記です。** このリポジトリでの再測定は含みません。
> 測定条件・未測定の範囲は下記の該当節に転記し、引用は [引用索引](../../../reference/cross-repo-index.md) に登録済みです。
> **保留していた 1 点は解消しました。** KeepAlive の間隔は引用先の 2 文書が桁の違う値を持っていた間、
> 桁でも書いていませんでした。訂正が入り、**旧値は撤回として明示されています。**

## NFS / SMB 経由の書き込みに対する動作

**FPolicy は動作するイベントソースです。** 限界の列挙だけを読むと機構自体が使えないように見えますが、成立する条件があります。

| 観点 | 測定された挙動 |
|---|---|
| 通知の遅延 | **サブ秒**（正確な値は引用先） |
| 遮断 | ファイルプロトコル経由なら `mandatory` モードで実際に拒否されます |
| セッションの継続 | **72 時間の連続観測 1 回で、自発的な切断 0 件**。新規セッションは開始時の 1 本だけ |

### 測定条件

**条件を外した数値は設計に使えません。** 引用先の環境は次のとおりです。

| 項目 | 値 |
|---|---|
| リージョン | `ap-northeast-1` |
| デプロイタイプ / スループット | `SINGLE_AZ_1` / 128 MBps / SSD 1024 GiB |
| ONTAP バージョン | `9.18.1P3D1` |
| FPolicy サーバー | ECS Fargate 1 タスク、0.25 vCPU / 512 MB、`linux/amd64` |
| FPolicy プロトコル版 | ネゴシエーション結果で `1.2` |
| engine の設定 | `asynchronous`、`ssl_option=no_auth` |
| 観測窓 | 72.01 時間（1 回） |

**タスクは 1 本で、窓の間ずっと同じタスクが `RUNNING` のままでした。** タスク置換を挟んだ場合の挙動は、この測定には含まれません。

## 動かし続けるための運用要件

**FPolicy は「有効にすれば動き続ける」機構ではありません。** 4 点が運用に乗ります。

### 外部サーバの必須性と NLB を前段に置けない理由

外部エンジンとして動かす FPolicy は、**イベントを受け取るサーバーを自分で用意する必要があります。** そのサーバーの前段に Network Load Balancer を置いて可用性を得る構成は成立しません。

**ONTAP はタスクの ENI のプライベート IP へ TCP で直接つなぎます。** FPolicy が独自のバイナリプロトコルを使うためで、NLB を経由させると接続の安定性に影響します。引用先の構成では **NLB は ECS Fargate タスクのヘルスチェック専用**（TCP 9898）で、イベントの経路には入っていません。

### engine が IP で登録されることの帰結

ONTAP は外部エンジンを **`primary-servers` に IP アドレスで保持します。** ホスト名ではありません。

**したがってタスクが置き換わるたびに再登録が必要です。** Fargate のタスクは再起動で新しい IP を受け取るので、登録が古いままだと接続が切れたままになります。引用先は EventBridge が ECS のタスク状態変化を拾い、Lambda が ONTAP REST API で `primary-servers` を更新する形を実装しています。

**接続を開くのが ONTAP 側であることは、経路設計では消せません。** 収集側から到達性を足しても解決しない点は [クロスアカウントは IAM ではなくネットワークの問題](../../observability/notes/cross-account-is-a-network-problem.md#収集元の数を決めるのは接続の向き) と同じ論点です。

### 再起動時の欠落窓

**タスクの再起動から再登録の完了までは、イベントが失われます。** 引用先は復旧の所要を**分の桁**として記録しています（正確な値は引用先）。

**取り込みに使う場合、この窓は「読み込まれないファイル」です。** 監視のダッシュボードなら穴として見えますが、取り込みパイプラインでは**そのファイルが存在しないのと同じ**になります。窓の間に着地したファイルを後から回収する手段を、設計に別途持つ必要があります。

### 健全性の指標が届く間隔と、診断窓の下限

**接続が生きていることは KeepAlive で分かります。届く間隔は分の桁です**（正確な値は引用先。
ONTAP の既定は `keep_alive_interval` に従います）。

**そして診断の窓をその間隔より狭くすると、健全なパイプラインを異常と報告します。** 引用先は窓が
`keep_alive_interval` を超えている必要があると明記していて、**既定より狭い窓では健全な接続が
高い確率で「何も出ない」ように見えます。** 通知が来ないことと、窓が短いことを区別できません。

**この間隔には撤回された旧値があります。** 引用先の一方が桁の違う短い値を載せていた期間があり、
**実測で再現せず撤回されました。** 撤回の記述は引用先に残っているので、**古い値を根拠にした
監視設定が現場にある可能性を前提にしてください。**

### enabled ポリシーの変更不可

**有効なポリシーは変更できません。** 監視するイベントや scope を後から変えるには `disable` → 変更 → `enable` の順になり、**その窓の操作は捕捉されません。**

**つまり監視対象を変える作業それ自体が欠落を作ります。** scope はポリシー作成時にインラインで与える必要があり、後から scope だけを POST すると 404 になります。

## 本番アーキテクチャの 4 パターン

引用先は 4 つのパターンを整理しています。**実際に走らせたのはパターン 1 だけです。** 残りは設計であって測定ではありません。

| # | 構成 | 引き受けるもの | 測定 |
|---|---|---|---|
| 1 | 単一 Fargate タスク | 単一障害点。再起動で IP が変わり、分の桁の欠落窓 | **実行済み** |
| 2 | primary / secondary による ONTAP ネイティブのフェイルオーバー | タスク 2 本の費用。両方の IP 更新。`event_id` による重複排除が必要になりえます | 未測定 |
| 3 | EventBridge による engine IP の突き合わせ | Lambda から ONTAP 管理エンドポイントへの到達性と、engine を変更できる資格情報 | 未測定 |
| 4 | マルチ AZ 配置 | AZ 障害時の影響範囲がファイルシステムのデプロイタイプに依存します | 未測定 |

**パターン 2 は ONTAP 側の機能です。** 外部エンジンが `primary-servers` と `secondary-servers` を受け付け、primary に到達できないとき ONTAP がフェイルオーバーします。**AWS 側のロードバランサでは代替できません**（前述のとおり前段に置けないため）。

## 取り込みで起きる固有の誤読

**ファイル名で突き合わせると、S3 Access Point 経由の書き込みが発火したように見えます。**

S3 Access Point で書いたファイルを後からファイルプロトコルで読むと、**その読み取りに対して同じファイル名の通知が出ます。** 名前で突き合わせる実装は、これを書き込み時の通知と区別できません。

**突き合わせはタイムスタンプで行う必要があります。** 名前で照合したまま「S3 経路でも FPolicy は動いている」と結論すると、実際には遮断も検知も効いていない構成を動いていると判定します。

## 引用元が未測定としている範囲

**引用は都合のよい部分だけを取り出せます。** 引用先が明示している空白をそのまま転記します。

| 未測定の範囲 | 影響 |
|---|---|
| **72 時間を超えた挙動** | 「セッションは切れない」への一般化はできません。測ったのは 1 回・1 構成・72 時間です |
| **engine IP を再登録した後の挙動** | 再登録が継続性に与える影響は別の問いとして残っています |
| **ロードバランサを前段に置いた場合** | 置けないという記述は構成上の理由に基づき、置いた場合の測定はありません |
| **パターン 2 / 3 / 4** | 設計として整理されており、実行されていません |
| **KeepAlive の間隔以外の健全性指標** | **KeepAlive の有無しか測られていません。** 遅延の増大や欠落の部分的な発生を検出する手立ては測定範囲の外です |
| S3 Access Point 経由の遮断 | 通知が無いため、遮断の可否は「該当しない」であって測定結果ではありません |

**環境は窓の確認後に削除されています。** ログ保持は 30 日ですが、ロググループが Fargate スタックの資源なのでスタックと一緒に消えます。**再検査できるのは集計と、削除前に取得した窓全体のサーバーログのエクスポートだけです。**

## 自環境での確認手順

| # | 手順 | 確認できること |
|---|---|---|
| 1 | 書き込みが着地するプロトコルを経路ごとに書き出す | **FPolicy が適合するかどうか。** 読む側は判定に入りません |
| 2 | 同じボリュームに NFS / SMB と S3 Access Point の両方で書き、通知の有無を比べる | 経路による差が自環境でも出ること |
| 3 | event の protocol に `s3` を指定してみる | HTTP 400 で拒否されること（[プロトコル集合の再確認](../../security-governance/notes/access-point-authorization-layers.md#この経路を見ない-fpolicy)） |
| 4 | FPolicy サーバーのタスクを意図的に置き換え、再登録までの時間を測る | **自環境での欠落窓の桁** |
| 4b | `keep-alive-interval` を engine から読み、監視・診断の窓がそれより広いか確認する | **健全な接続を異常と報告しないこと。** 窓が狭いと「通知が来ない」と区別できません |
| 5 | 手順 4 の窓の間に着地したファイルを、後から回収できるか試す | **取り込みに使う場合の穴の埋め方があるか** |
| 6 | ポリシーの scope を変更してみる | `disable` → 変更 → `enable` になること、その窓が欠落すること |
| 7 | 通知をファイル名ではなくタイムスタンプで突き合わせる | 読み取り由来の通知を書き込みと誤認しないこと |

**手順 5 を設計段階で行わないと、欠落の存在を運用開始後に知ります。**

## よくある誤解

| 誤解 | 実際 |
|---|---|
| FPolicy は S3 Access Point 経由の操作に効かないので、イベントソースとして使えない | **NFS / SMB 経由の書き込みには動きます。** 判定は着地するプロトコルで、機構の可否ではありません |
| 読む側が S3 Access Point なら FPolicy は使えない | **読む側は判定に入りません。** 書き込みが NFS / SMB で着地していれば発火します |
| 外部サーバの前段に NLB を置けば可用性が上がる | **置けません。** ONTAP がタスクの ENI へ直接つなぐため、NLB はヘルスチェック専用です。冗長化は ONTAP の `secondary-servers` 側です |
| engine はホスト名で登録できる | **IP アドレスです。** タスクが置き換わるたびに再登録が要ります |
| 有効にすればイベントは連続する | **再起動で分の桁の欠落窓が出ます。** 取り込みではそのファイルが存在しないのと同じです |
| 監視対象は稼働中に変更できる | **enabled のポリシーは変更できません。** `disable` → 変更 → `enable` の窓は捕捉されません |
| 通知はファイル名で突き合わせればよい | **読み取りでも同じ名前の通知が出ます。** タイムスタンプで突き合わせてください |
| KeepAlive が見えなければ接続が切れている | **窓が `keep_alive_interval` より狭いだけの場合があります。** 既定より短い窓では、健全な接続が高い確率で「何も出ない」ように見えます |
| 本番構成は実測済みである | **実行されたのは単一タスクのパターンだけです。** 残る 3 つは設計です |
