# 実験ブランチを配るときに縛る対象は権限だけではない

[🏠 リポジトリトップ](../../../../../README.md) | [Domain — セキュリティ / ガバナンス](../README.md)

---

## 結論

**データサイエンティストや解析エンジニアに Snapshot とクローンを使わせるために、`fsxadmin` を渡す必要はありません。** SVM 単位の操作は `vsadmin` で足り、ONTAP REST API は SVM の管理エンドポイント経由で呼べます。**プラットフォーム側が `vsadmin` として呼び、利用者はその窓口を叩く形にできます。**

**しかし権限を絞るだけでは足りません。縛る対象は 3 つあります。**

| 縛る対象 | 縛らなかったときに起きること |
|---|---|
| **認可** — 誰がどの SVM に対して何を実行できるか | 範囲外のボリュームを触れる |
| **資源** — 総量として何本・どれだけの帯域まで許すか | **クローンは親の QoS 制限を継承しないため、実験ブランチが本番の帯域を食います** |
| **寿命** — 作ったものがいつ消えるか | ボリューム数の上限（1 HA ペア 500、合計 1,000）に到達し、**本番のボリュームが作れなくなります** |

**3 つのうち資源と寿命は、権限の設計では止まりません。** 「クローンを作る権限を与えるかどうか」と「クローンが本番を巻き込むかどうか」は別の問題です。

そして **不可逆な操作をこの窓口に載せてはいけません。** Snapshot のロックや SnapLock は、成功しても取り消せません。

> **Evidence**: `hypothesis` — **この運用モデルは未検証です。** 構成要素それぞれの挙動には出典がありますが
> （`vsadmin` の範囲、ONTAP REST API の経路、QoS ポリシーグループ、ボリューム数の上限）、
> **これらを組み合わせた自己サービスの窓口を実際に構築・運用した結果ではありません。**
> とくに「ONTAP REST API 経由の操作が CloudTrail に現れるか」は**確認していません**（下記に明記しています）。
> 責務分割の整理は参照記事に依拠していますが、**その記事も実装提案であり検証結果ではないと明記しています。**
> 検証の出発点として使ってください。**設計の根拠にする前に、[自環境での確認手順](#自環境での確認手順) を通してください。**

## 背景 — 最初に来る「管理者権限を渡すのか」という問い

Snapshot・クローン・ストレージ API が AI のワークフローに入ってくると、**最初に出る懸念は権限です。** データサイエンティストにストレージの管理者権限を渡すのか、という問いです。

**渡す必要はありません。** ただし「渡さない」を実現する形は 1 つではなく、**どこで境界を引くかを決める作業が残ります。**

FSx for ONTAP 側には境界を引ける層が既にあります。

| 層 | 範囲 |
|---|---|
| `fsxadmin` | ファイルシステム（クラスタ）全体 |
| `vsadmin` | 個別の SVM |

**`vsadmin` のパスワードを設定していない環境では、結局 `fsxadmin` を使うことになります。** SVM 作成時に設定してください。理由は [管理者を分ける](what-the-platform-gives-and-what-stays-yours.md#権限設計--管理者の分離) にあります。

## 責務の分割

**利用者が要求するのは結果で、方針を強制するのはプラットフォーム、操作を実行するのは基盤という分け方です。**

| 誰が | 何を持つか |
|---|---|
| ストレージ / プラットフォーム管理者 | 認可の設計、サービスアカウントとその範囲、許可する操作の定義、命名規約、容量とボリューム数の割り当て、保持期間、ネットワークとプロトコルの経路、監査ログ、監視と例外処理 |
| AI / 解析の利用者 | ノートブックの拡張、内部データポータル、DataOps / MLOps のパイプライン、承認済みのコマンドライン、統制されたエージェント |

**利用者は「このデータセットの版から実験ブランチを作りたい」と要求し、プラットフォームが要求を検証して、絞られたサービス識別情報で承認済みの操作を実行します。**

この整理は参照記事の提案と同じです。**このノートの追加分は、FSx for ONTAP でそれを実装しようとしたときに、権限以外に何を縛る必要があるかです。**

## 縛る対象 1 — 認可

| 決めること | 使える仕組み | 注意 |
|---|---|---|
| どの SVM を対象にするか | `vsadmin` は SVM 単位 | **`fsxadmin` を配ると範囲を後から絞り直すのが難しくなります** |
| プラットフォームが何で呼ぶか | ONTAP REST API（SVM の管理エンドポイントに HTTPS） / ONTAP CLI（SSH） | **クローンと FlexCache はテンプレートからは届きません。** [IaC の境界は API の表面で決まる](../../../playbooks/04-build/notes/what-iac-cannot-reach.md) |
| 利用者に何を見せるか | ノートブック拡張、データポータル、パイプラインのアクション | 利用者が直接インフラのコマンドを打たない形にします |

**SVM を用途で分ける設計が、この層で最も効きます。** 学習データ用の SVM と本番共有用の SVM を分ければ、`vsadmin` の範囲がそのまま境界になります。

## 縛る対象 2 — 資源

**ここが権限設計では止まらない部分です。**

**クローンは親ボリュームに設定した QoS ポリシーグループの制限を継承しません。** つまり **「本番ボリュームに上限をかけてあるから安全」は成り立ちません。** 利用者が作ったクローンは、その制限の外にいます。

| 縛るもの | 手段 | 型の選択 |
|---|---|---|
| 帯域と IOPS の総量 | QoS ポリシーグループ | **共有型 (`-is-shared true`)。** グループ全体の合計が上限になるため、**本数が読めなくても総量が決まります** |
| 本数 | 割り当てとして管理する | **1 HA ペアあたり 500 本、全 HA ペア合計 1,000 本。** FlexGroup のコンスティチュエントも同じ枠を使います |
| 容量 | ボリュームのサイズと、共有が解けた分の消費 | クローンは共有部分の容量を消費しませんが、変更した分は消費します |

**非共有型で「1 本あたりの上限」を決めても総量は決まりません。** 30 本作られれば 30 本分の要求が乗ります。

**`is-shared` は既存のポリシーに対して変更できません。** 共有型に変えるには新しいポリシーを作ってボリュームの参照先を差し替えるので、**窓口を開ける前に型を決めてください。**

**ボリューム数を割り当てとして管理する必要があるのは、上限が共有資源だからです。** 実験ブランチが枠を使い切ると、**本番のボリュームが作れなくなります。** 数え方と FlexGroup との関係は [学習データセットの版をスケジュール Snapshot に載せると消える](../../data-utilization/notes/dataset-versions-and-experiment-branches.md) にあります。

## 縛る対象 3 — 寿命

**作ったものが消えないと、資源の割り当ては時間とともに必ず枯れます。**

| 決めること | 状況 |
|---|---|
| クローンの保持期限 | **ONTAP 側に「クローンの最大寿命」を強制する設定があるかは確認していません。** 現時点では、期限の管理はプラットフォーム層の責務として実装する前提で考えてください |
| 版として作った Snapshot の保持 | スナップショットポリシーとは別に作るため、**回転で消えません。** 消す判断も別に必要です |
| 放置されたクローンの検出 | 作成時刻と最終アクセスを持ち、期限切れを一覧できるようにします |

**期限切れの削除は「消してよいか」の判断を含みます。** 実験の結果がまだ使われているクローンを消すと作業が失われるので、**削除の予告と猶予を持つ形が必要です。** ここは未検証の設計領域です。

**そして SSD 容量の縮小操作と同時に走らせないでください。** 縮小操作の開始後に作られたクローンがあると縮小が一時停止し、**再開にはそのクローンの削除が必要になります。** コスト削減の作業が、利用者のクローンによって止まります。

## この窓口に載せてはいけない操作

**成功しても取り消せない操作は、自己サービスの対象外です。**

| 操作 | 理由 |
|---|---|
| Snapshot のロック（tamperproof snapshot） | **AWS API 側に該当するパラメータがなく、IAM の条件キーやコンソールの警告で止められません。** SnapLock ボリュームでなくても効きます |
| SnapLock の有効化、`SnaplockType`、監査ログボリューム、`PrivilegedDelete` | 保持期間が切れるまで削除できず、**影響範囲がボリュームを超えて SVM とファイルシステムに及びます** |
| 保持期間を伴う設定全般 | 「動いていること」と「障害を起こしたこと」が区別できません |

**理由と、承認を作業の承認と分けて取る手順は [不可逆な操作の承認は作業の承認とは別に取る](irreversible-operations-need-separate-approval.md) にあります。** データセットの版を守る目的でも、この経路には載せないでください。

## 監査で答えられる範囲と答えられない範囲

**自己サービスにする以上、「誰が何をしたか」を後から言える必要があります。** ここには**確認できていない点があります。**

| 問い | 状況 |
|---|---|
| 誰がファイルシステムやボリュームを作成・削除したか（Amazon FSx API 経由） | CloudTrail が記録します |
| **誰が ONTAP REST API / ONTAP CLI 経由でクローンを作ったか** | **未検証です。** CloudTrail が記録するのは Amazon FSx の API 呼び出しで、SVM の管理エンドポイントへの HTTPS リクエストは AWS の API 呼び出しではありません。**したがって現れない可能性が高いと考えていますが、確認していません** |
| 誰がどのファイルを読んだか | ファイルアクセス監査で記録できます |
| 誰がそのファイルを**何回**読んだか | **答えられません。** 1 オブジェクトにつき最初の読み取りと最初の書き込みだけが記録されます |

**この 2 行目が、この運用モデルで最も先に確かめるべき項目です。** 監査の経路が CloudTrail だけを前提にしていると、**自己サービスの窓口を通った操作がどこにも残らない構成になりえます。** その場合、記録はプラットフォーム層のアプリケーションログとして自分で作る必要があります。

監査の 2 つの面と 4663 の仕様は [監査は 2 つの面に分かれ、片方に穴があります](what-the-platform-gives-and-what-stays-yours.md#監査の-2-つの面と片方の穴の存在) にあります。

## エージェントに実行させる場合の扱い

**同じ窓口を使わせてください。** エージェントに直接インフラの権限を渡すのではなく、人間の利用者と同じ制約付きのサービス層を通します。

| ガードレール | 内容 |
|---|---|
| 対象の限定 | 触れるデータセットとボリュームを明示的に列挙する |
| 操作の限定 | 許可する操作を列挙する。**不可逆な操作は含めない** |
| 資源の上限 | 共有型 QoS と、割り当てたボリューム数の枠 |
| 寿命 | クローンの最大保持期間 |
| 承認 | 昇格（本番への反映）と削除は人間の承認を要求する |
| 記録 | すべての操作を追跡可能な形で残す |

**「エージェントだから危険」ではなく、「窓口を経由しないから危険」です。** 人間に許していない操作をエージェントに許さない、という一点で足ります。

## 効果の主張に必要な測定項目

**このモデルの価値は容量削減ではなく、待ち時間と手戻りの削減として現れます。** そして **このノートはどれも測っていません。** 主張する前に基準値を取ってください。

| 測る項目 | なぜこれか |
|---|---|
| 実験の要求から、使えるデータセットが用意できるまでの中央値 | 自動化の効果が最も直接に現れます |
| データが用意できていないために止まっている計算資源の時間 | 高価な学習環境が空転している時間 |
| 誤ったデータセットの版で実行して失敗したジョブの数 | 版管理が効いているかの代理指標 |
| 実験 1 件あたりのストレージ関連の問い合わせ件数と対応工数 | 手渡しがどれだけ残っているか |
| 過去の実験を再構成するのに要した時間 | 版が残っていることの価値 |
| 学習データとの対応が完全に追えるモデルの割合 | リネージの網羅率 |
| 実際に作っていたフルコピーの本数と総容量 | **作っていなかったなら、削減ではなく「増えなかった」です** |

**業界水準の投資対効果をそのまま自分の環境に当てないでください。** とくに歩留まり改善のような大きな経済効果は、プロセスの知見・モデルの品質・データの品質・運用の定着に依存します。**データ基盤はその前提条件を満たす側で、効果そのものの帰属先ではありません。** 参照記事も同じ注意を書いています。

## このモデルの未検証な点

**明示しておきます。以下はいずれも確認していません。**

| 未検証の項目 | 確かめる方法 |
|---|---|
| ONTAP REST API 経由の操作が CloudTrail に現れるか | 下記の手順 1 |
| クローンの最大寿命を ONTAP 側で強制できるか | ONTAP のドキュメントとバージョンごとの差を確認する |

## 自環境での確認手順

**最初に確かめるのは、記録が残るかです。** 権限を絞っても記録が残らなければ、自己サービスは監査に耐えません。

| # | 手順 | 確認できること |
|---|---|---|
| 1 | ONTAP REST API または ONTAP CLI でクローンを 1 本作り、**同じ時刻の CloudTrail を検索する** | **その操作が記録されるか。** 記録されない場合、プラットフォーム層で自分でログを作る必要があります |
| 2 | `vsadmin` のパスワードが設定済みかを確認する | `fsxadmin` を配らずに運用できるか |
| 3 | `vsadmin` で SVM の管理エンドポイントに接続し、**範囲外の SVM のボリュームが見えないことを確認する** | 認可の境界が実際に効いているか |
| 4 | 親ボリュームに QoS を設定してクローンを作り、クローン側の QoS 設定を確認する | **継承しないことの実測。** 窓口を開ける前に必要です |
| 5 | 共有型のポリシーをクローン 2 本に適用し、合計が上限で止まることを確認する | 総量を縛れているか |
| 6 | 現在のボリューム数を数え、実験ブランチに割り当てられる残り本数を出す | 枠として管理できる数 |
| 7 | 期限切れのクローンを検出する手段があるかを確認する | 寿命を管理できるか。なければ実装対象です |
| 8 | 同じファイルを 2 回読み、2 回目が監査ログに現れないことを確認する | 監査で答えられる範囲 |

**手順 1 と 4 を最初に置いています。** どちらも「窓口を開けてから気づくと、開け直しになる」項目です。

適用手順の全体像は [本番に取り入れる前の確認](../../../evidence-policy.md#本番に取り入れる前の確認) を参照してください。

## よくある誤解

| 誤解 | 実際 |
|---|---|
| Snapshot やクローンを使わせるには管理者権限が必要 | SVM 単位の操作は `vsadmin` で足ります。プラットフォームが代理で実行する形にできます |
| 権限を絞れば本番への影響は防げる | **クローンは親の QoS を継承しません。** 権限の外に資源の問題が残ります |
| 本番ボリュームに QoS をかけてあるので安全 | その制限はクローンに引き継がれません |
| 非共有型の QoS で 1 本あたりを決めれば総量も決まる | 本数に比例して総量が増えます。**総量を縛るなら共有型です** |
| QoS の型は後から変えられる | **`is-shared` は既存ポリシーで変更できません。** 作り直して差し替えます |
| クローンは容量を使わないので放置してよい | **ボリューム数の上限を消費します。** 枯れると本番のボリュームが作れなくなります |
| 版を守るためにロックを自動化するとよい | **不可逆な操作です。** この窓口に載せず、承認を分けて取ります |
| CloudTrail があるので操作は全部追える | CloudTrail は Amazon FSx の API 呼び出しです。**ONTAP REST API 経由の操作が現れるかは未検証です** |
| エージェントには専用の強い権限を用意する | 人間の利用者と**同じ窓口・同じ制約**を通します |
| 削減額は導入前に見積もれる | 実際に作っていたフルコピーの本数を測ってからでないと、削減か「増えなかった」かが区別できません |
