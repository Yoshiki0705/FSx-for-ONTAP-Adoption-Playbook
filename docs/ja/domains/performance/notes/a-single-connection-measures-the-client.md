# 単一接続で測った値はストレージの性能ではない

[🏠 リポジトリトップ](../../../../../README.md) | [Domain — 性能](../README.md)

---

## 結論

**マウントを 1 つ張って測った値は、ストレージの性能ではなく EC2 の 1 フローあたりの帯域上限です。**

sibling プロジェクトの実測で、**製品もプロトコルも違う 3 つの構成が単一接続でいずれも 4.0〜4.7 Gbps に収まりました。** AWS は 1 ネットワークフローあたり全二重 5 Gbps の上限を明記しており、**3 つとも同じものを測っていた**ということです。

**接続を増やすと、当たる上限が 2 段に分かれます。** 読むデータがファイルサーバーのキャッシュから返るならネットワークの上限に、キャッシュに無いならディスクの上限に当たります。**どちらに当たるかは作業セットとキャッシュの大小で決まり、製品でも世代でもプロトコルでもありません。**

**そして同じ構成が同じ条件で 45% 振れました。** 同一設定・同一パラメータファイル・同一測定器で 2 回測って 3,551.18 と 5,148.56 MB/s。違いはキャッシュに何が残っていたかだけです。

**帰結は 1 つです。このファイルシステムのスループットを 1 つの数字で書くことはできません。** 書くなら接続数・データ共有の有無・キャッシュの温まり方を併記します。

> **区分**: `documented` — 数値は [S3-Burst-on-ONTAP-Files のプロトコル別測定結果](https://github.com/Yoshiki0705/S3-Burst-on-ONTAP-Files/blob/main/docs/ja/verification/perf-matrix-results.md) からの引用です。**このリポジトリでは再測定していません。** 分担の原則は [プロジェクト間の引用索引](../../../reference/cross-repo-index.md) にあります。
> **引用元の測定環境は削除済みです。** 再現手順は引用元に残っています。

## 測定条件

**条件を外した数値は使えません。** 以下は引用元が記録しているものをそのまま並べます。

| 項目 | 値 |
|---|---|
| 測定日 | 2026-09-05 |
| リージョン | `ap-northeast-1`、単一 AZ、**全ターゲットと全クライアントが同一サブネット** |
| ONTAP | 9.18.1P5 |
| FSx for ONTAP | 第 2 世代 `SINGLE_AZ_2`、**6,144 MBps × 1 HA ペア**、SSD 4,096 GiB、プロビジョンド 200,000 IOPS |
| NVMe リードキャッシュ | **無効**（両ノードで確認済み） |
| `tcp-max-xfer-size` | **1,048,576 へ引き上げ済み。既定 65,536 のままだと `rsize` が 64 KiB に切り下がります** |
| ボリューム | NFS 用 900 GiB / UNIX、SMB 用 900 GiB / NTFS。階層化なし・インライン効率化なし |
| テストデータ | 非圧縮。FSx for ONTAP 600 GiB、Amazon EFS 300 GiB |
| クライアント | `c5n.9xlarge`（Linux / Windows とも同一型）。ネットワーク 50 Gbps は保証値 |
| 測定器 | VDBENCH 5.04.07。並列度 512 スレッド |

**SSD を 4,096 GiB にしているのは容量のためではなく IOPS のためです。** ここを小さくすると、測っているものが変わります。

## 単一接続で揃ってしまう値

1 MiB 逐次読みです。

| 構成 | 接続数 | スループット | 応答時間 |
|---|---|---|---|
| FSx for ONTAP NFSv4.1、`nconnect=16` | 16 | **3,551〜5,149 MB/s** | 144.18 / 99.44 ms |
| FSx for ONTAP SMB 3.1.1、Multichannel 有効 | 4 | 2,227.61 MB/s | 229.78 ms |
| Amazon EFS、マウントヘルパー経由 | 1 + プロキシ | 1,495.82 MB/s | 342.28 ms |
| FSx for ONTAP NFSv4.1、`nconnect` なし | 1 | 591.62 MB/s | 865.40 ms |
| FSx for ONTAP SMB 3.1.1、Multichannel 無効 | 1 | 574.24 MB/s | 891.60 ms |
| Amazon EFS、素の `mount -t nfs` | 1 | 499.79 MB/s | 1,024.41 ms |
| Amazon EFS、`nconnect=16` | — | **I/O が停滞して測定不能** | — |

**下の 3 行を Gbps に直すと揃います。**

| 単一接続の実測 | Gbps 換算 | 公表の 1 フロー上限 |
|---|---|---|
| FSx for ONTAP NFS 591.62 MB/s | 4.7 Gbps | 5 Gbps |
| FSx for ONTAP SMB 574.24 MB/s | 4.6 Gbps | 5 Gbps |
| Amazon EFS 素マウント 499.79 MB/s | 4.0 Gbps | 5 Gbps |

**単一接続で 2 製品を比べて出た 1.18 倍は、両方でこの上限を測った結果です。** 製品の差ではありません。

**表の読み方に 2 つ注意があります。** 1 つ目、**上の 3 行と下の 3 行は接続数が違うので、製品の優劣を読み取る表ではありません。** 2 つ目、**最上段が幅を持っているのは測定誤差ではなく、キャッシュの状態差です**（後述）。

Amazon EFS の `nconnect=16` が測定不能だったことについては、**引用元がその挙動を再現し、クライアント側でサーバー単位にキャッシュされる性質として記録しています。** マウントオプションの組み合わせの問題で、製品の帯域の話ではありません。詳細は引用元を読んでください。

## 2 段の上限

**接続を増やしたあとに当たる上限は 2 つあり、公表値と突き合わせるとどちらも説明できます。**

| 経路 | 公表値（この構成） | 実測 | 達成率 |
|---|---|---|---|
| ネットワーク（キャッシュから返る読み） | 12,500 MBps（ベースライン、バーストなし） | 12,763 MBps | **102%** |
| ディスク（キャッシュに無い読み） | 3,072 MBps | 2,411 MBps | 78% |

**注目すべきは、この構成のスループット容量が 6,144 MBps だという点です。** ネットワークのベースラインは 12,500 MBps で、**スループット容量の設定値とは別の数字です。** スループット容量が何を決めているかは [スループットは 1 つの設定値では決まらない](where-throughput-is-determined-and-shared.md) にあります。

**どちらの上限に当たるかは、データを共有しているかどうかで変わりました。** 8 台・128 接続での実測です。

| 8 台・128 接続 | 合計 | 比 |
|---|---|---|
| 全台が同じファイルを読む | 11,916.29 MB/s | — |
| 各台が重ならない領域を読む | 2,173.37 MB/s | **0.18 倍** |

**違いはデータを共有しているかどうかだけです。** 共有していれば 1 回のディスク読み取りが全台を満たせます。AWS も **SSD の IOPS が使われるのはファイルサーバーのメモリ / NVMe キャッシュに無いデータへアクセスするときだけ**と書いています。

**同じファイルシステム・同じワークロード形状・同じ接続数で 5.5 倍変わります。** 性能要件を「MB/s」だけで書くと、この 5.5 倍のどちらを指しているのか決まりません。

---

## 45% の幅の正体

**同一設定・同一パラメータファイル・同一測定器で 2 回測って 3,551.18 と 5,148.56 MB/s でした。** 違いはキャッシュに何が残っていたかだけです。

**これはベンチマークの再現性の問題ではなく、このストレージの性質です。** キャッシュから返るかどうかで上限の段が変わるので、**測定の順序と直前に何を読んだかが結果を決めます。**

| 対策 | 内容 |
|---|---|
| キャッシュを外して測る | **NVMe リードキャッシュを無効化する。** 引用元はそうしています。**AWS も高スループット時は無効化を推奨しています** |
| 作業セットをキャッシュより大きくする | テストデータの合計はサーバー台数倍になります。台数とファイルサイズの両方で決まります |
| 測定前の状態を記録する | 直前に何を読んだかを含めて記録しないと、2 回目が 1 回目と比較できません |
| 幅で報告する | **1 点で報告すると、都合のよい側を選んだのと区別が付きません** |

## 性能要件の書き方

**「MB/s」だけの要件は、この実測を見たあとでは決まりません。** 決めるべき項目です。

| 決めること | 決めないと何が起きるか |
|---|---|
| 接続数（`nconnect` / SMB Multichannel のチャネル数） | **単一接続なら約 5 Gbps で止まります。** 製品を替えても同じです |
| データを共有するか、各ホストが別の領域を読むか | **同条件で 5.5 倍変わります** |
| 作業セットとキャッシュの大小関係 | 当たる上限の段が変わります |
| ブロックサイズと並列度 | 引用元は 1 MiB / 512 スレッドで測っています |
| クライアントの型 | **`c5n.9xlarge` の 50 Gbps は保証値です。** バースト型では測定対象がクライアントになります |
| `tcp-max-xfer-size` | **既定のままだと `rsize` が 64 KiB に切り下がります** |

**最初に上げるべきは接続数です。** `nconnect` なし 591.62 MB/s から `nconnect=16` で 3,551〜5,149 MB/s まで動いています。**設定 1 つで最も大きく動いた項目でした。**

## 引用元が未測定としている範囲

**引用は都合のよい部分だけを取り出せます。** 引用元が未測定として挙げているものを、そのまま持ってきます。

| ケース | 状態 |
|---|---|
| キャッシュ状態をそろえた再測定 | **未測定。上の 45% の幅を畳むために最も価値があるとされています** |
| 第 1 世代と第 2 世代の世代差（NFSv4.1 固定） | 未測定 |
| S3 API と NFS で同一データを比べる測定 | 未測定 |
| 重ならない領域での台数試験の 1 台と 6 台 | 未測定（2 / 4 / 8 台は実測） |
| SMB Multichannel のチャネル数を 4 より増やす条件 | 未測定（`max_connections_per_session=32` でも 4 だった） |
| 64 KiB 逐次読みが 64 KiB ランダム読みより遅い理由 | 未測定 |

**測定環境は削除済みです。** 作り直す手順は引用元のリポジトリにあります。

## 自環境での確認手順

**引用元と同じ数字を目標にしないでください。** 構成が違えば当たる上限が違います。

| # | 手順 | 確認できること |
|---|---|---|
| 1 | マウントの接続数を数える（`nconnect` の値、SMB は `Get-SmbMultichannelConnection`） | **単一接続なら約 5 Gbps で止まります** |
| 2 | `nfs show -vserver <svm> -fields tcp-max-xfer-size` | **既定 65,536 なら `rsize` が切り下がります** |
| 3 | 作業セットのサイズとファイルサーバーのキャッシュ容量を比べる | どちらの上限に当たるか |
| 4 | 同じ測定を 2 回連続で回し、差を見る | **キャッシュの温まり方による幅。1 回だけでは分かりません** |
| 5 | クライアントを 1 台と複数台で測り、ONTAP 側の物理ポートのカウンタと突き合わせる | **クライアント側の合計は証拠になりません** |
| 6 | 全台が同じデータを読む場合と、重ならない領域を読む場合を分けて測る | 5.5 倍の差がどちら側か |
| 7 | クライアントのネットワークが保証値かバーストかを確認する | **バースト型では測定対象がクライアントになります** |

手順 5 は引用元がそうしています。**クライアント側の集計だけでは、詰まっている場所を分離できません。**

## よくある誤解

| 誤解 | 実際 |
|---|---|
| マウントを 1 つ張って測ればストレージの性能が分かる | **EC2 の 1 フロー上限を測っています。** 製品もプロトコルも違う 3 構成が 4.0〜4.7 Gbps に収まりました |
| プロトコルの選択が性能を決める | **接続数のほうが大きく動きました**（591.62 → 3,551〜5,149 MB/s） |
| 製品間の 1.18 倍は製品の差 | **両方で同じ 1 フロー上限を測っていました** |
| スループット容量の設定値が到達できる上限 | **この構成では 6,144 MBps 設定でネットワークのベースラインが 12,500 MBps でした。** 別の数字です |
| ベンチマークが 45% 振れたのは測定ミス | **キャッシュに何が残っていたかの差です。** このストレージの性質です |
| 台数を増やせば線形に伸びる | **データを共有しているかで 5.5 倍変わります** |
| 1 つの数字で性能を書ける | **書けません。** 接続数・共有の有無・キャッシュの状態を併記します |
| 引用元と同じ構成なら同じ数字が出る | **キャッシュの温まり方までそろえないと出ません** |
