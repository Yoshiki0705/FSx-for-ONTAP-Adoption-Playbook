# Harvest は remote_write を持たない

[🏠 リポジトリトップ](../../../../../README.md) | [Domain — 可観測性](../README.md)

---

## 結論

**NetApp Harvest を選ぶと、収集基盤そのものの運用が自分に来ます。** その内容は 4 面に分かれます。

| # | 面 | 内容 |
|---|---|---|
| 1 | 転送方式 | **エクスポータは Prometheus のプルエンドポイントと InfluxDB。** Amazon Managed Service for Prometheus へは 1 ホップ挟みます |
| 2 | 可用性 | AWS 提供の CloudFormation テンプレートは **Amazon EC2 1 台**。監視面が単一障害点になります |
| 3 | 資格情報 | **`fsxadmin` の資格情報で ONTAP に認証します。** 収集対象を増やすとロック時の影響範囲が広がります |
| 4 | 初期設定 | Grafana の初期資格情報が既知の値です。ログイン後の変更が推奨されています |

**このノートは 4 面をまとめて扱います。** ファイル名は 1 面目だけを指していますが、いずれも「収集基盤の運用が自分に来る」という同一の論点の各面です。

> **Evidence**: `documented` — 4 面すべて公式ドキュメントの記載に基づきます（**取得日 2026-09-05**）。**著者による実測は含みません。**

---

## エクスポータの選択肢と remote_write の不在

Harvest の Prometheus エクスポータの役目は 2 つと明記されています。**メトリクスを Prometheus のライン形式に整形すること**と、**`http://<ADDR>:<PORT>/metrics` に web エンドポイントを作ること**です。そして「**Prometheus が Harvest をポーリングする**」と書かれています。

つまり **Harvest は送りません。取りに来られる側です。**

| 方式 | Harvest の対応 |
|---|---|
| Prometheus のプル（スクレイプ） | 対応。エンドポイントを公開します |
| InfluxDB への書き込み | 対応。別のエクスポータとして用意されています |
| Prometheus の `remote_write` | **公式ドキュメントに記載がありません**（2026-09-05 時点、Harvest 25.08 のエクスポータのドキュメントを対象に確認） |

> **確度に関する補足**: 上の 3 行目は「ドキュメントに記載が見つからない」という**ドキュメントについての事実**です。将来の版で追加される可能性を否定するものではありません。自分の版で確認する手順は下の [自環境での確認手順](#自環境での確認手順) にあります。

## Amazon Managed Service for Prometheus へ入れる 1 ホップ

Amazon Managed Service for Prometheus は `remote_write` で受け取ります。Harvest は `remote_write` で送りません。**したがって間に 1 ホップが必要になります。**

必要な構成要素:

| 要素 | 役割 |
|---|---|
| スクレイパ | Harvest の `/metrics` を取得する側 |
| SigV4 署名 | Amazon Managed Service for Prometheus の `remote_write` エンドポイントへの認証 |
| そのスクレイパを動かす基盤 | Amazon EC2、コンテナ、またはマネージドのスクレイパ |

**この 1 ホップは「設定を足す」ではなく「運用対象を 1 つ足す」です。** 監視のための構成要素が落ちたことに気づく仕組みも要ります。

構築手順とテンプレートは [fsxn-observability-integrations](https://github.com/Yoshiki0705/fsxn-observability-integrations) にあります。**このノートで扱うのは「何が必要になるか」までです。**

## 監視面の単一障害点

AWS が提供する CloudFormation テンプレートは、**Harvest と Grafana をインストールした Amazon EC2 Linux インスタンスを 1 台作成する**構成です。既定のインスタンスタイプは `t3.micro` です。

| 観点 | 内容 |
|---|---|
| 構成 | Amazon EC2 1 台に Harvest と Grafana |
| 意味 | **そのインスタンスが落ちると監視が止まります。** 監視対象は動き続けます |
| 必要な受信ポート | 3000（Grafana）、9090（Prometheus）、53 TCP/UDP（DNS）、443 TCP（HTTPS） |

**監視が止まったことを検知する仕組みは、この構成の外側に置くことになります。** 監視面の死活を監視対象と同じ経路で見ていると、両方同時に見えなくなります。

> **設計に関する補足**: このテンプレートは導入の速さを狙ったものです。1 台構成であること自体は前提であり、可用性が要件なら構成を変える判断が先に来ます。

## ロック時の影響範囲を決める収集対象数

CloudFormation テンプレートのパラメータには **AWS Secrets Manager のシークレット名**があり、そこに **ファイルシステムの `fsxadmin` ユーザーのパスワード**を格納します。つまり **Harvest は管理アカウントで ONTAP に認証します。**

ここが監視固有のリスクです。**ONTAP は認証失敗の繰り返しで管理アカウントをロックします。** ロックすると管理操作が止まります（データ経路は影響を受けません）。原因・復旧手順・閾値の設定は [fsxadmin はロックされる](../../../playbooks/05-operate/notes/admin-account-lockout-and-recovery.md) にあります。

**監視を広げるときに変わるのは影響範囲です。**

| 構成 | ロック時に止まるもの |
|---|---|
| 1 ファイルシステムを 1 つの収集元から監視 | そのファイルシステムの管理操作 |
| 複数ファイルシステムを同じ資格情報で監視 | **同じ資格情報を使う全ファイルシステムの管理操作** |
| 収集の失敗時にリトライが即座に繰り返される | **認証失敗が積み上がり、ロックの引き金になりえます** |

設計に入れる項目:

| 項目 | 理由 |
|---|---|
| 対象ごとの資格情報分離 | 1 つのロックが全対象に波及しないようにするため |
| 認証失敗時のバックオフ | リトライ自体がロックの原因になりうるため |
| シークレット更新とパスワード再設定の順序 | 逆順にすると収集側が古い値で認証を続けます |
| ロック検知の経路 | 管理操作が止まったことを、管理経路以外から知る必要があります |

## 初期資格情報の変更

デプロイ後の Grafana へは `http://<EC2 のアドレス>:3000` でアクセスし、**Grafana の既定のユーザー名とパスワード**でログインする手順が公式ドキュメントに記載されています。ドキュメント自身が**ログイン後すぐの変更を推奨**しています。

| 項目 | 状態 |
|---|---|
| Grafana の初期資格情報 | 公開ドキュメントに記載された既知の値 |
| 受信ポート 3000 | テンプレートの前提として開放 |
| 組み合わせた結果 | **到達できる範囲から既知の資格情報でログインできる状態が、変更するまで続きます** |

> **セキュリティに関する補足**: サブネットの種別（`public` / `private`）とセキュリティグループの許可元は、テンプレートのパラメータで指定します。**既定値ではありません。** 到達範囲を絞る判断は導入時に行う必要があります。

## 自環境での確認手順

| # | 手順 | 確認できること |
|---|---|---|
| 1 | 導入する Harvest の版のエクスポータのドキュメントを開き、`remote_write` の記載を検索する | **自分の版での対応状況。** このノートは 25.08 時点の記載です |
| 2 | Harvest の `/metrics` エンドポイントに直接アクセスする | プル方式であることと、出ているメトリクスの実物 |
| 3 | Amazon Managed Service for Prometheus に入れる場合、スクレイパを止めて欠測が出ることを確認する | **1 ホップが単一障害点かどうか** |
| 4 | 監視用インスタンスを停止し、どの通知が飛ぶかを確認する | **監視面の死活を検知できているか。** 何も飛ばないなら検知していません |
| 5 | 収集対象ごとに使っている資格情報を洗い出す | ロック時の影響範囲の実数 |
| 6 | 収集側の認証失敗時の挙動（間隔とリトライ回数）を設定値で確認する | バックオフが効いているか |
| 7 | Grafana の初期資格情報が変更済みか確認する | 導入直後の状態が残っていないか |
| 8 | Grafana とセキュリティグループの許可元 CIDR を確認する | 到達範囲 |

**手順 4 が最も飛ばされます。** 監視面が落ちたことに気づかない構成は、監視が無い状態と区別できません。

## よくある誤解

| 誤解 | 実際 |
|---|---|
| Harvest から Amazon Managed Service for Prometheus に直接送れる | **エクスポータはプルエンドポイントと InfluxDB です。** スクレイパ + SigV4 の 1 ホップが要ります |
| Harvest がメトリクスを送信する | **Prometheus が Harvest をポーリングします。** 取りに来られる側です |
| 1 ホップは設定を足すだけ | **運用対象が 1 つ増えます。** それ自体の死活監視も要ります |
| AWS のテンプレートは本番構成である | **Amazon EC2 1 台です。** 可用性が要件なら構成を変える判断が先に来ます |
| 監視の追加は読み取りだけなので安全 | **`fsxadmin` で認証します。** 認証失敗の積み上がりはロックの引き金になりえます |
| 収集対象を増やしてもリスクは変わらない | **同じ資格情報を共有していれば、1 つのロックが全対象に波及します** |
| Grafana の初期資格情報は自動生成される | 公開ドキュメントに記載された既知の値です。変更が推奨されています |
| テンプレートが到達範囲を絞ってくれる | サブネット種別と許可元はパラメータです。導入時の判断です |
