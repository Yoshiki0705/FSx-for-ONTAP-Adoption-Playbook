# 経路選定チェックリスト

[🏠 リポジトリトップ](../../../../../README.md) | [Domain — 可観測性](../README.md)

---

## このチェックリストの位置づけ

Amazon FSx for NetApp ONTAP の監視経路を決める前に確認する項目です。**監視設計の網羅的な一覧ではありません。** 収録の基準は 1 つで、**確認しないまま進めると経路の作り直しになるかどうか**です。

閾値の置き方や統計値の選択は経路を決めた後の作業で、[監視は平均値で失敗する](../../../playbooks/05-operate/notes/monitoring-fails-on-averages.md) にあります。

> **Evidence**: `documented` — 各項目の根拠は AWS / ベンダーの公式ドキュメントに基づきます（**取得日 2026-09-05**）。**当リポジトリでの実測は含みません。** 「実測」と書いた項目は読者が測るものです。

---

## 1. 所在と認証 — 後から変えられない条件

- [ ] **データを AWS の VPC の外に出せるか**を監査要件と照らして確定した。**出せないなら SaaS 経路が落ちます。** 粒度は後から足せますが、出したデータを出さなかったことにはできません
- [ ] SaaS を検討する場合、[データの所在についての確認事項](../../../reference/comparison/observability-routes.md#データの所在についての確認事項) の 7 件に回答した。**遵守の判断は法務・コンプライアンスの領域です**
- [ ] SaaS を検討する場合、**選定時点の提供リージョン**を各ベンダーの最新のドキュメントで確認した。**過去の情報は選択肢を狭く見積もります**
- [ ] 選んだ SaaS で、**選択したリージョン以外に置かれる情報**の有無を確認した
- [ ] 収集されるメトリクスのラベルに**ボリューム名・共有名・パス**が含まれるかを実物で確認した（実測）。**設定だけでは分かりません**
- [ ] 画面を見せる相手が **ID プロバイダ側に存在する**か確認した。Amazon Managed Grafana は匿名アクセスをサポートしません
- [ ] 自社ポータルへの埋め込み要件がある場合、**IdP 起点ログインの現状**を最新のドキュメントで確認した。[経路は認証とアクセス経路で先に狭まる](../notes/route-choice-is-bounded-by-access-and-auth.md#amazon-managed-grafana-の認証方式)

---

## 2. 見たいものと、取れるもの

- [ ] **現在見ている画面と指標を列挙**した。移行後に失うものを数えるための入力です
- [ ] 手順 1 の各指標が **AWS の公開メトリクスで再現できるか**を照合した
- [ ] 再現できなかった指標を **Harvest の非サポート 10 種**と突き合わせた。[オンプレのダッシュボードはそのまま移らない](../notes/on-prem-dashboards-do-not-transfer.md)
- [ ] **Health と Headroom を使っていた場合**、代替の指標を決めた。**この 2 つの不在は運用設計を変えます**
- [ ] 必要な画面が**既定で無効な 8 種**に含まれるか確認した。含まれる場合は有効化の作業が発生します
- [ ] サポート対象のダッシュボードで**空欄になるパネル**を記録した（実測）。分類だけでは分かりません
- [ ] **レイテンシのテール（p99）が要件か**確認した。要件ならクライアント側の測定が別途必要です。[p99 は CloudWatch のメトリクスからは出せない](../../performance/notes/what-you-cannot-read-from-cloudwatch.md)
- [ ] 経路 4 を検討する場合、**欲しい値の数**を数えた。判断の閾値は台数ではなく**保守を続けられるか**です

---

## 3. 収集基盤 — 経路 2 を選ぶ場合

- [ ] 導入する **Harvest の版**を確定した。ダッシュボードの構成は版で変わります
- [ ] Amazon Managed Service for Prometheus を使う場合、**スクレイパ + SigV4 の 1 ホップ**を構成に含めた。Harvest は `remote_write` で送りません
- [ ] **監視面の死活を検知する仕組み**を、監視対象と別の経路に置いた。AWS 提供テンプレートは Amazon EC2 1 台構成です
- [ ] 監視用インスタンスを停止して**通知が飛ぶことを確認**した（実測）。飛ばないなら検知していません
- [ ] **監視対象数と有効化するテンプレート数**を数え、既定構成からの増分を出した
- [ ] サイジングについて、**出典間の食い違い**（AWS: 10 台あたり 2 コア / メモリ 1 GB / ディスク 500 MB、ベンダーブログ: 4 vCPU / 16 GB）を認識し、自分の要件で判断した。**どちらもベンダーの推奨値で実測値ではありません**
- [ ] 収集中の **CPU・メモリ・ログ増加量**を実測し、推奨値との差を記録した（実測）
- [ ] `t3` 系を使う場合、**収集が重なる時間帯のクレジット残高**を確認した（実測）
- [ ] **Grafana の初期資格情報を変更**した。公開ドキュメントに記載された既知の値です
- [ ] Grafana とセキュリティグループの**許可元 CIDR** を確認した。到達範囲はパラメータで、既定値ではありません

---

## 4. 資格情報 — 監視が管理面に持ち込むリスク

- [ ] 収集が **`fsxadmin` の資格情報で ONTAP に認証する**ことを認識した。読み取りだけの操作ではありません
- [ ] **収集対象ごとに資格情報を分離**した。共有していると 1 つのロックが全対象に波及します
- [ ] 認証失敗時の**バックオフ**を設定した。リトライ自体がロックの原因になりえます
- [ ] **シークレット更新とパスワード再設定の順序**を決めた。逆順にすると収集側が古い値で認証を続けます
- [ ] **ロックを検知する経路**を、管理経路以外に用意した
- [ ] 復旧手順を確認した。[fsxadmin はロックされる](../../../playbooks/05-operate/notes/admin-account-lockout-and-recovery.md)

---

## 5. ONTAP の API

- [ ] 自分の版で **ZAPI が有効か**確認した。**アップグレード後 30 日間使われなければ自動的に無効化されます**
- [ ] 性能メトリクスを使う場合、版が **9.12.1 以降**か確認した
- [ ] 「ZAPI は廃止済み」という前提で設計していない。**提供終了は無期限に延期されています**。[ZAPI の提供終了の無期限延期](../notes/route-choice-is-bounded-by-access-and-auth.md#zapi-の提供終了の無期限延期)

---

## 6. 到達したい規模

- [ ] **到達したい段階（1: PoC / 2: 単一アカウント / 3: クロスアカウント / 4: クロスプラットフォーム）を先に決めた**
- [ ] 段階 3 を想定する場合、**ネットワーク到達性の問題**であることを認識した。IAM の設定ではありません
- [ ] 段階 3 の構成要素（Transit Gateway、RAM 共有、**双方向の**静的ルート、両側のセキュリティグループ）を洗い出した
- [ ] 段階 4 を想定する場合、**Transit Gateway で到達できるか**を確認した。到達できないなら分散型の設計になります
- [ ] 段階 4 を想定する場合、**拠点ごとの ONTAP の版**を並べ、取れるメトリクスがそろうか確認した
- [ ] 段階 4 が視野にある場合、**段階 1 の構成から分散を前提**にした。後から上げると作り直しになります
