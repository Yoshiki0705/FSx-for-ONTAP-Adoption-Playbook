# 第三者バックアップ製品が届く経路は AWS の API 側ではない

[🏠 リポジトリトップ](../../../../../README.md) | [Domain — データ保護](../README.md)

---

## 結論

**「既存のバックアップ製品を使っているので、FSx for ONTAP も同じ運用で入る」は、経路を確認してから言えることです。**

ある製品の資料を読むと、**同じ製品が FSx for ONTAP に届く経路と、他の Amazon FSx ファミリーに届く経路が違います。** 前者は AWS Backup を経由するクラウドネイティブな経路から**名指しで除外**されており、ファイル共有側の機能へ案内されています。

**そして「対応」の書き方が経路ごとに違います。** 一方は非対応の明示、もう一方は**対応システムの列挙に載っていない**という状態です。**この 2 つは根拠の強さが違い、後者を非対応と読むことはできません。**

読者が確認すべき問いは 2 つです。

1. **その製品はどの経路で届くのか。** AWS の API 経由か、ONTAP の管理面経由か、ファイル共有経由か
2. **「対応していない」と書かれているのか、それとも「書かれていない」のか**

> **区分**: `documented` — ベンダーの公開文書の記載に基づきます（**取得日 2026-09-15**）。**当リポジトリで製品の動作を検証していません。** 経路が成立するかどうかも確認していません。ここにあるのは資料が何を述べているかで、動作の確認ではありません。
> **1 製品の資料から読み取った構造です。** 他の製品が同じ構造を持つとは主張しません。下の [自環境での確認手順](#自環境での確認手順) は、製品を問わず立てられる問いとして書いています。

---

## 3 つの経路と、資料の書き方の差

| 経路 | 何を経由するか | FSx for ONTAP | 資料の書き方 |
|---|---|---|---|
| **1. AWS プラグイン**（クラウドネイティブ） | AWS Backup サービス | **除外** | 「Amazon FSx for NetApp ONTAP のクラウドネイティブバックアップの作成に対応しない」と名指しで記載。Backup & Replication のコンソールへ案内されています |
| **2. ONTAP プラグイン**（Universal Storage API） | ONTAP の管理面 | **列挙に無い** | 対応システムの列挙は FAS / AFF / ASA / ASA r2（ONTAP 9.10.1 以降）。**FSx for ONTAP は書かれていません** |
| **3. Unstructured Data Backup**（NAS） | ファイル共有（NFS / SMB） | 経路 1 の文書がここへ案内 | 「Backup & Replication のコンソールを使って FSx for ONTAP ファイルシステムをバックアップできる」と記載 |

**経路 1 が除外されている意味は、AWS の API から見えなくなることです。** 経路 1 は AWS Backup サービスを使って Amazon FSx のバックアップとバックアップコピーを作る形で、AWS Backup 側で Amazon FSx リソースタイプのオプトインを有効にする必要があります。**FSx for ONTAP はこの形に乗りません。**

**経路 3 はファイル共有として扱う形です。** つまり **NFS / SMB で見えるものが対象**になり、ボリューム全体やボリュームの構成そのものではありません。**LUN の中身はファイルプロトコルに現れない**ので、ブロックで出しているデータがこの経路の対象になるかは、別に確認する必要があります（[LUN の中身はファイルプロトコルに現れない](../../block-storage/notes/lun-contents-do-not-reach-file-protocols.md)）。**この点は資料に書かれておらず、こちらで確認していません。**

---

## 明示的な除外と列挙の不在の区別

**経路 1 と経路 2 は、読者が引ける結論の強さが違います。**

| 経路 | 資料の状態 | 引ける結論 | 引けない結論 |
|---|---|---|---|
| 1 | 非対応が名指しで書かれている | 「この経路では作成できない」 | — |
| 2 | 対応システムの列挙に無い | 「列挙に載っていない」 | **「非対応である」** |

**列挙の不在を非対応と読むことは、このリポジトリが根拠に使ってはいけないものとして挙げている読み方です**（[適合条件 — 根拠に使ってはいけないもの](../../../reference/fsx-ontap-fit-conditions.md)）。列挙は更新されますし、載っていない理由は非対応・未評価・記載漏れのいずれもありえます。

**ベンダーへの照会は行っていません。** 経路 2 が使えるかどうかを確定させたい場合、それが手段になります。

**経路 2 に付随する他の要件は評価していません。** 資料には FlexClone ライセンスの必要性、組み込み統合との併存規則、Tamperproof Snapshot がクラスタ単位の登録を要すること（SVM 単位では不可）などが書かれていますが、**FSx for ONTAP が列挙に無いので、これらが当てはまるかを判断できません。** 当てはまると仮定して設計しないでください。

**経路 1 の制約に、不可逆な設定が経路を閉じる例が含まれています。** 同じ文書に「logically air-gapped vault と AWS Backup Vault Lock を有効にした vault にはクラウドネイティブバックアップを保存できない」と記載されています。**これは経路 1 の制約なので FSx for ONTAP を直接縛りません**が、**コンプライアンス目的で入れた不可逆な設定がツールの保存先を外す**という形が、同じ資料の中に実例として存在します。Vault Lock は [不可逆な操作の承認は作業の承認とは別に取る](../../security-governance/notes/irreversible-operations-need-separate-approval.md) の対象です。

## AWS ネイティブの手立てとの対称な比較

**第三者製品を足さない選択も同じ重みで置きます。** どちらにも引き受けるものがあります。

| 手立て | 向く状況 | 引き受ける制約 |
|---|---|---|
| **FSx for ONTAP のボリュームバックアップ + AWS Backup** | AWS の制御面で完結させたい。既存の AWS Backup の運用に載せたい | **復元するまでファイルシステムを持ちません。** 別リージョン・別アカウントへの経路には境界があります（[バックアップコピーは復元するまでファイルシステムを持たない](backup-copies-across-regions-and-accounts.md)） |
| **ONTAP の Snapshot + SnapMirror** | 粒度と RPO を細かく決めたい。ONTAP の機能をそのまま使いたい | **制御面が ONTAP 側になります。** Snapshot があることと復旧できることは別です（[Snapshot があることと復旧できることは別](snapshots-are-not-a-recovery-plan.md)） |
| **第三者製品（ファイル共有経由）** | 既存のバックアップ基盤に集約したい。他のワークロードと同じカタログで管理したい | **経路が AWS の API ではありません。** 対象はファイル共有から見えるものになり、ライセンスと運用主体が増えます |

**選び方は「どれが優れているか」ではなく、集約の要件があるかどうかです。**

| 手元の状況 | 素直な選択 |
|---|---|
| 既存のバックアップ基盤に集約する要件が無い | **AWS ネイティブ側。** 製品を足さない選択が最も運用が軽くなります |
| 集約が要件で、対象がファイル共有から見える | 第三者製品。**ただし経路を先に確認する** |
| 集約が要件で、対象にブロック（LUN）が含まれる | **ファイル共有経由では見えません。** 別の手立てを検討します |
| 監査やコンプライアンスで不可逆な保持設定を入れる予定がある | **その設定が製品の保存先を外さないかを、設定する前に確認する** |

## 自環境での確認手順

**製品を問わず立てられる問いとして書いています。**

| # | 手順 | 確認できること |
|---|---|---|
| 1 | その製品が FSx for ONTAP に届く経路を、資料の中で特定する | **AWS の API 経由か、ONTAP の管理面経由か、ファイル共有経由か** |
| 2 | 「対応していない」と書かれているのか、「書かれていない」のかを区別する | 引ける結論の強さ |
| 3 | 経路がファイル共有なら、対象データが NFS / SMB から見えるかを確認する | **ブロックで出しているデータは対象外の可能性** |
| 4 | 経路が ONTAP の管理面なら、管理エンドポイントへの到達性と資格情報の要件を確認する | `fsxadmin` の権限境界に当たるか |
| 5 | 不可逆な保持設定を入れる予定があるなら、その設定が保存先の対象から外れないかを先に確認する | **設定してからでは戻せません** |
| 6 | 列挙に無いだけの場合、ベンダーに照会する | **列挙の不在は非対応の証拠ではありません** |
| 7 | 経路が確定したら、復元を実際に試す | **バックアップが取れることと戻せることは別です** |

**手順 5 を後回しにすると、コンプライアンス側の要求を満たした結果としてバックアップ経路が閉じます。**

## よくある誤解

| 誤解 | 実際 |
|---|---|
| 既存のバックアップ製品を使っているので同じ運用で入る | **経路が違う場合があります。** 資料の中で経路を特定してください |
| Amazon FSx に対応しているなら FSx for ONTAP にも対応している | **ファミリー単位ではありません。** クラウドネイティブな経路から名指しで除外されている例があります |
| 対応システムの列挙に無いので非対応である | **引けません。** 非対応・未評価・記載漏れのいずれもありえます |
| ファイル共有経由なら中のデータはすべて対象になる | **NFS / SMB から見えるものが対象です。** LUN の中身はファイルプロトコルに現れません |
| 第三者製品を入れれば AWS ネイティブ側は不要になる | 目的が違います。**集約の要件が無いなら、製品を足さない選択が最も軽くなります** |
| 不可逆な保持設定はバックアップを強くするだけ | **ツールの保存先から外れる例があります。** 設定する前に確認してください |
| この記述は製品の動作の確認である | **資料が何を述べているかの整理です。** 当リポジトリで動作を検証していません |
