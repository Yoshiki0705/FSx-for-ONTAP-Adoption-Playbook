# 外部ツールのアーカイブと容量プール階層は代替ではなく順序を持つ

[🏠 リポジトリトップ](../../../../../README.md) | [Domain — コスト](../README.md)

---

## 結論

**「安くする手立て」を並べると、外部のデータ管理ツールによるアーカイブと FSx for ONTAP の容量プール階層が同じ列に見えます。しかし置かれる場所が違います。**

AWS Storage Blog が公開している事例では、**2 段が順序を持って効いています。** 最初にアクセス日時を基準に外部ツールが S3 Glacier へアーカイブし、**その後に残ったデータが容量プール階層へ下がっています。** 一方が他方の代わりに置かれてはいません。

**そして公開されている削減率の基準は、他の AWS 選択肢ではなく自社の旧環境です。** この事例は珍しく**脚注に構成を明記している**ので、率がどの構成に対する値かを読み取れます。**構成が違えば率は移りません。**

**引くべきものは率ではなく順序と、率に付いている条件です。**

> **区分**: `documented` — AWS が publish した事例の記載に基づきます（**取得日 2026-09-15**）。**当リポジトリでの実測は含みません。** 事例の数値は導入した組織の構成に対するもので、設計の根拠にはなりません。
> **記載された内訳の数字は足し合わせが合いません。** 下の [記録された順序と、合わない足し合わせ](#記録された順序と合わない足し合わせ) に記載しています。**率をそのまま引かないでください。**

---

## 記録された順序と、合わない足し合わせ

**事例に記録されている順序は次のとおりです。**

| 段 | 何が起きたか | 記載されている割合 |
|---|---|---|
| 1 | 移行後、**最終アクセス日時**を基準に最初のアーカイブを実行。外部ツールが S3 Glacier へ移動 | **約 70%** が S3 Glacier へ |
| 2 | FSx for ONTAP に残った分が、**30 日以内**に容量プール階層へ | 残った **30% のうち 60%** |
| 結果 | 記事の記載 | 「初期データの **90% 超**が最適化された」 |

**この 3 つの数字は足し合わせても 90% を超えません。** 70 + (30 × 0.6) = 88 です。**「最適化された」の数え方が書かれていないため、差分の理由が分かりません。** 記事の他の記述と矛盾するわけではなく、定義が示されていないという状態です。

**したがって引けるのは順序で、率ではありません。** 「アーカイブが先に大半を持っていき、容量プール階層が残りに効いた」という順序は 2 段の記述から読めます。**90% 超という合計は、定義が分かるまで引用しないでください。**

**順序が意味を持つ理由は、2 段が別の課金次元に効くことです。**

| 段 | 移動先 | 何が変わるか |
|---|---|---|
| 外部ツールのアーカイブ | Amazon S3 / S3 Glacier | **FSx for ONTAP の外へ出ます。** ファイルシステムの容量から抜けます |
| 容量プール階層 | FSx for ONTAP の容量プール階層 | **ファイルシステムの中に残ります。** SSD 階層から下がるだけで、**リクエストにも課金されます** |

**容量プール階層のリクエスト課金があるため、下げれば必ず安くなるとは限りません。** 繰り返し読み直すデータを下げると高くなります。詳細は [階層化が常に安くなるとは限らない理由](provisioned-versus-consumed.md#階層化が常に安くなるとは限らない理由) にあります。**この事例の脚注は容量プール階層のリクエスト数を前提として明記しています**（下記）。

---

## 削減率の基準と、脚注に書かれた構成

**率は「$1/GB/年 に達していた旧環境」に対する 50% 超です。** 他の AWS ファイルストレージとの比較ではありません。**比較の基準が明記されている事例は多くないので、この点が引く価値のある部分です。**

脚注に記載されている構成は次のとおりです。

| 項目 | 記載値 |
|---|---|
| FSx for ONTAP のデータ | 768 TB |
| バックアップ | 768 TB |
| SSD 階層の割合 | 30% |
| スループット | 8 GBps |
| SSD IOPS | 320,000 |
| 容量プール階層の読み書きリクエスト | 600 万 |
| S3 Glacier Instant Retrieval のデータ | 4.2 TB |
| 月あたりの取り出し | 10 TB |
| **含まれている費用** | **NetApp と外部ツールの第三者ライセンス費**を含む |
| 比較の基準 | **$1/GB/年** の旧環境 |

**第三者ライセンス費が内訳に含まれている点が重要です。** ツールを足す判断は、削減額からライセンス費を引いた後で評価されます。**ライセンス費を除いた率ではありません。**

**この構成が自環境と違えば率は移りません。** 特に次の 3 つが動くと結果が変わります。

| 動くと結果が変わるもの | なぜ |
|---|---|
| **SSD 階層の割合（30%）** | 確保した SSD 容量には確保の時点で課金されます。割合が上がれば率は下がります |
| **容量プール階層のリクエスト数（600 万）** | **リクエストにも課金されます。** 読み直しが多い構成では下げても安くなりません |
| **比較の基準（$1/GB/年）** | 旧環境がこれより安ければ、削減率は小さくなります |

**「50% 削減」を自環境の見積もりに使わないでください。** 引けるのは「基準と構成を明記した事例が存在する」ことと、上の 3 つが率を動かすという構造です。

**移行速度について記事は「最大 25 倍」と記載していますが、何に対する倍率かが書かれていません。** 基準が無いので、この数値は設計にも比較にも使えません。

## 移行手段の選定理由の所在

**この事例が外部ツールを移行に使った理由は、機能の比較ではなく移行元の所在です。** 記事は AWS Snowball と AWS DataSync を候補として挙げた上で、**「データの大半がすでにクラウドプロバイダにホストされていた」ため外部ツールを使ったと記載しています。**

**つまり移行手段の選定は、ツールの機能より前に移行元で決まっています。** この順序は既存の [移行方式の選択](../../../reference/decision-trees/migration-method.md) と同じで、**製品の比較から入ると順序が逆になります。**

記事が挙げているツール側の選定理由は、耐障害性、移行中に利用者が元の場所でもクラウド上でもデータを見つけられること、規制対象部門向けの chain-of-custody レポートです。**これらは機能の記載で、当リポジトリで確認したものではありません。**

**構成上の前提が 2 つあります。** 外部ツールは中央のリージョンの Amazon EC2 上で動いており、**単一リージョンで許容された**構成です。また **FlexCache の性能には AWS Direct Connect が要件**とされており、無い場合は最初に着手すべき項目としてリードタイムが挙げられています。

## AWS ネイティブの手立てとの対称な比較

**外部ツールを足さない選択も同じ重みで置きます。**

| 手立て | 向く状況 | 引き受ける制約 |
|---|---|---|
| **容量プール階層のみ**（FSx for ONTAP の機能） | ファイルシステムの中で完結させたい。ツールを増やしたくない | **ファイルシステムの外へは出ません。** リクエスト課金があり、読み直しが多いと下がりません |
| **外部ツールによるアーカイブ** | ファイルシステムの外（S3 / Glacier）へ出したい。利用状況の可視化も要る | **ライセンス費と運用主体が増えます。** 事例では EC2 上で運用されています |
| **両方**（事例の構成） | 大半を外へ出し、残りを階層で下げたい | **上の 2 つの制約を両方引き受けます。** 順序と閾値の設計が要ります |

**選び方は、データがファイルシステムの外へ出てよいかどうかです。**

| 手元の状況 | 素直な選択 |
|---|---|
| データがファイルシステムの外へ出てはいけない | **容量プール階層のみ。** 外部ツールのアーカイブは選択肢から外れます |
| 読み直しの頻度が高い | **階層化で下げると高くなる場合があります。** [階層化が常に安くなるとは限らない理由](provisioned-versus-consumed.md#階層化が常に安くなるとは限らない理由) を先に読んでください |
| 利用状況の可視化そのものが目的 | 外部ツール側。**ただし可視化は階層化とは別の要件です** |
| 旧環境の単価が既に低い | **削減率は事例より小さくなります。** 基準が違います |

## 自環境での確認手順

| # | 手順 | 確認できること |
|---|---|---|
| 1 | 旧環境の GB あたり年額を出す | **比較の基準。** これが無いと率を語れません |
| 2 | データがファイルシステムの外へ出てよいかを監査要件と照らす | **出せないなら外部ツールのアーカイブは落ちます** |
| 3 | 最終アクセス日時の分布を測る | 段 1 でどれだけ動くか。**事例の 70% は事例の分布に対する値です** |
| 4 | 段 1 の後に残る分の読み直し頻度を測る | **段 2 で下げると高くなるかどうか** |
| 5 | 容量プール階層のリクエスト数を見積もる | 脚注の 600 万と自環境の差 |
| 6 | 第三者ライセンス費を削減額から引く | **ツールを足す判断の実際の効果** |
| 7 | 移行元がどこにあるかを確定させる | **移行手段はここで決まります。** ツールの機能比較より前です |
| 8 | FlexCache を使う予定があるなら Direct Connect の有無とリードタイムを確認する | 事例が最初の着手項目として挙げている点 |

**手順 1 を飛ばすと、削減率という言葉が意味を持ちません。**

## よくある誤解

| 誤解 | 実際 |
|---|---|
| アーカイブと容量プール階層はどちらかを選ぶもの | **順序を持ちます。** 事例では外部ツールのアーカイブが先に効き、残りが容量プール階層へ下がっています |
| 50% 削減は FSx for ONTAP にすれば得られる | **基準は自社の旧環境（$1/GB/年）です。** 旧環境が安ければ率は小さくなります |
| 事例の 90% 超という合計を引用できる | **記載された内訳を足し合わせても 88% です。** 数え方が書かれていないので引用できません |
| 削減率にツールの費用は含まれていない | **含まれています。** 脚注に第三者ライセンス費込みと記載されています |
| 階層化すれば必ず安くなる | **リクエストに課金されます。** 読み直しが多いと高くなります |
| 移行ツールは機能で選ぶ | **事例の選定理由は移行元の所在です。** 機能比較より前に決まっています |
| 「最大 25 倍」は移行速度の目安になる | **何に対する倍率かが書かれていません。** 基準が無いので使えません |
| 事例の構成をそのまま自環境の見積もりに使える | **SSD 割合・リクエスト数・比較の基準が動くと率が変わります** |
