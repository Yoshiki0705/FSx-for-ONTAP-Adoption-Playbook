# AI のコストはトークン単価だけで決まるか？

決まりません。コンピューティング・ストレージ・データベース・キャッシュ・人件費が隣接コストとして乗ります。FSx for ONTAP はこの隣接コストのうち、ストレージとキャッシュに効く選択肢の 1 つです。

## このノートで学べること

- AI ワークロードのコストが「トークン単価」だけで決まらない理由と、トークン隣接コスト（adjacent cost）の構成。
- Tokenomics という業界標準が、いま何を定義しようとしているか（2026-08 設立、策定中の段階）。
- FSx for ONTAP が隣接コストのどこに効き、どこには効かないか。

## このノートが答えないこと

- モデル別のトークン単価、AI サービスの月額、自環境の見積もり。単価は改定されます。
- 「FSx for ONTAP を使えば AI コストが下がる」という一般化。効く条件は限定されます。
- Tokenomics の未確定の仕様（Big-T Framework、認定プログラムなど）の内容。ロードマップにある事実のみ扱います。

### 結論

**AI ワークロードのコストは、トークンそのものの単価だけでは決まりません。** 業界で形成されつつある整理（Tokenomics）は、AI コストの大半がトークン単価ではなく、コンピューティング・ストレージ・データベース・キャッシュ、そしてそれを構築する人件費といった**隣接コスト**（adjacent cost）にあると位置づけています。

トークンは「一貫した最小使用単位」として全体に現れますが、請求書の全体ではなく一部です。

**FSx for ONTAP はこの隣接コストのうち、ストレージとキャッシュに効く選択肢の 1 つ**です。RAG・推論・学習のデータをどのプロトコルで、どこに置き、何回読むかが、リクエスト単価（cost per call）と全体の TCO に効きます。「これが最適解」ではなく、「どの状況でどの軸に効くか」を整理します。

> **Evidence**: `documented` — Tokenomics の骨子は Linux Foundation の公式発表に基づきます（**取得日 2026-11-09**）。
> **Tokenomics Foundation は 2026-08-04 設立で、仕様は策定中です。** 確定済みの仕様としては扱えません。
> トークン単価・AI サービス価格は載せません。モデル更新ごとに計算式が変わると公式が明言しています。

### トークン隣接コストの構成

**AI の総コストは、トークン課金・コンピューティング・ストレージ・データ・人件費に分かれます。** Tokenomics の整理では、トークンは目に見える一部であり、隣接コストが総コストの大きな部分を占めると位置づけられています。

| コストの層 | 何か | FSx for ONTAP が効くか |
|---|---|---|
| トークン課金 | 推論の入出力トークンの単価 | 効きません。モデルとプロバイダの選択の領域です |
| コンピューティング | 推論・学習の GPU / CPU 時間 | 間接的。データ待ちで GPU が遊ぶ時間を減らせる場合があります |
| **ストレージ** | 学習データ・RAG のソース・ベクトル・中間成果物の保管 | **効きます。** 確保と消費の区分、階層化、重複排除・圧縮 |
| **キャッシュ** | 繰り返し読まれるデータの再利用 | **効きます。** FlexCache によるキャッシュ再利用 |
| データベース | メタデータ・インデックス・ベクトルストア | 構成によります。FSx for ONTAP 上に置く場合に限ります |
| 人件費 | パイプラインの構築・運用 | 間接的。コピージョブの削減が運用の手数に効きます |

**確保課金と消費課金の区分は AI ワークロードでも変わりません。** SSD 容量・スループットは確保した量で、容量プールとバックアップは消費した量で課金されます。詳細は [課金は「確保した量」と「使った量」に分かれる](provisioned-versus-consumed.md) にあります。**AI のデータは「書いたら頻繁に読まれる」ものと「一度書いて滅多に読まれない」ものが混在する**ため、階層化の判断がそのまま効きます。

### Tokenomics が定義しようとしているもの

**Tokenomics Foundation は、AI 支出と価値を結びつける共通の手法を、ベンダー中立で作ることを掲げています。** 2026-08-04 設立、技術推進委員会はこれから。**現時点では仕様は策定中**で、確定済みとして設計の前提に据えることはできません。公開済みのロードマップにある骨子は次のとおりです。

| 取り組み | 内容 | 確度 |
|---|---|---|
| **定義** | トークノミクスとは何か。入力・出力・推論・キャッシュを含むトークンの価値と密度（density）の定義 | ロードマップに掲げられている |
| **AI 総コストのリファレンスモデル** | トークン単体にとどまらず、コンポーネント全体を可視化するモデル | ロードマップに掲げられている |
| **サービス提供コスト（cost to serve）** | トークン単価ではなく、1 呼び出しあたりのコスト（cost per call）で BOM 全体を測る標準手法 | ロードマップに掲げられている |
| **価値の測定** | 人間の関与なしに完了した作業の割合を起点に、現在のプロセス費用と照らす AI Value Framework | ロードマップに掲げられている |
| **トークンコストのテレメトリ** | FOCUS v1.5 以降（FinOps Open Cost and Usage Specification）に AI コストレポートのスキーマを追加 | ロードマップに掲げられている |
| **Big-T Framework など** | モデルルーティング前にトークンと関連 AI コストの複雑性を分類する手法 | プロジェクトとして挙げられている（内容は未公開） |
| **教育・認定プログラム** | 実践者向けの基礎コースと資格認定 | ロードマップに掲げられている |

**cost per call がストレージ設計に効く理由**: 1 呼び出しあたりのコストで BOM 全体を測ると、RAG の 1 クエリが読むソースデータ・ベクトル・キャッシュの入出力が、トークン単価とは別の費目として可視化されます。**同じコンテキストを繰り返し読むワークロードでは、キャッシュ再利用が cost per call を直接下げます。** これが次の節につながります。

> **中立性に関する補足**: Tokenomics は特定のベンダーの手法ではなく、30 社の創設メンバーによるベンダー中立の業界標準を目指す取り組みです。**FSx for ONTAP を「Tokenomics に準拠した唯一の手段」とは書けません。** ここで扱うのは「隣接コストの整理に照らすと、ストレージとキャッシュの選択がどこに効くか」です。

### 隣接コストにおける FSx for ONTAP の効き所

**効くのはストレージとキャッシュで、効かないのはトークン単価です。** 効く場合も、データの読まれ方で向き不向きが分かれます。

| 効き方 | どの機構 | 効く条件 | 効かない / 逆効果になる条件 |
|---|---|---|---|
| **キャッシュ再利用** | FlexCache の NFS / SMB | 同じソースデータを繰り返し読む（RAG の共通コンテキスト、学習の epoch 反復） | 1 回しか読まないデータ。キャッシュが温まる前に捨てられる |
| **コピーの削減** | S3 Access Points / FlexCache | NAS 上のデータをコピーせず分析・AI から読む | コピーしたほうが到達が単純で、保管の重複コストより運用コストが勝つ場合 |
| **階層化** | 容量プールへのティアリング | 書いたら滅多に読まれない中間成果物・古い学習データ | 定期的に全件スキャンされるデータ。容量プールのリクエスト課金が積み上がる |
| **確保量の最適化** | 重複排除・圧縮 + 確保容量の縮小 | 効率化した分だけ確保容量を実際に下げられる | 効率化しても確保容量を下げなければ請求は変わりません |

**「AI だからストレージを多く確保する」が逆に効く場合があります。** SSD 容量は確保した量で課金されるため、学習データのピークに合わせて確保しっぱなしにすると、使っていない容量も請求されます。確保と消費の区分（[provisioned-versus-consumed](provisioned-versus-consumed.md)）が AI ワークロードでそのまま効きます。

**プロトコルと接続サービスごとの整理**（Bedrock・SageMaker・S3・DataSync 等）は、アクセス性・パフォーマンス・コストの 3 軸で [AI のアクセス経路別のコストと性能](access-path-cost-and-performance-by-service.md) にまとめてあります。

### よくある誤解

| 誤解 | 実際 |
|---|---|
| AI のコストはトークン単価でほぼ決まる | トークンは一部です。ストレージ・コンピューティング・キャッシュ・人件費が隣接コストとして乗ります |
| FSx for ONTAP を使えば AI コストが下がる | ストレージとキャッシュに効く条件があります。1 回しか読まないデータには効きません |
| 学習データ用に容量を多めに確保すれば安心 | SSD は確保量で課金されます。使っていない確保分も請求されます |
| 繰り返し読むデータは階層化すれば安くなる | 容量プールのリクエスト課金が積み上がります。繰り返し読むなら SSD かキャッシュが向きます |
| Tokenomics は確定した標準だ | 2026-08 設立で策定中です。ロードマップにある骨子を事実として扱い、未確定の仕様は前提にしません |
| cost per call はトークン課金のことだ | 1 呼び出しあたりの BOM 全体（データ入出力・キャッシュを含む）です。トークンはその一部です |
