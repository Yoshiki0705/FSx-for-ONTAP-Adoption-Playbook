# SMB ローカルユーザーに最終ログオン属性は無い。棚卸しは監査ログから起こすしかなく、削除の自動化は別の判断

[🏠 リポジトリトップ](../../../../../README.md) | [Domain — マルチプロトコル・ID](../README.md)

---

## 結論

**SMB ローカルユーザーのオブジェクトは、最終ログオン日時を持っていません。** CLI でも REST でも、取得できるのは次の項目だけです。

```text
FsxIdEXAMPLE::> vserver cifs users-and-groups local-user show -vserver <svm> -instance
                                   Vserver: <svm>
                               Domain Name: <cifs-server-name>
                                 User Name: <cifs-server-name>\wgaudit
                                 Full Name: Workgroup Audit Test
                               Description: -
                       Is Account Disabled: false
```

REST も `svm` / `sid` / `name` / `full_name` / `account_disabled` のみです。

**したがって「N か月使われていないアカウント」を知る経路は、ファイルアクセス監査ログしかありません。** これは AD 参加構成との明確な差です。AD 参加なら `lastLogonTimestamp` が使えるため、この作り込みは不要になります。

そして棚卸しを組むうえで、**監査ログ由来の「実績なし」は「不要」と同義ではありません。** 判定に使えるイベントの性質から誤検知が構造的に出ます。**削除の自動化は勧められません。**

> **Evidence**: `verified`（2026-09-01、`ap-northeast-1`、ONTAP `9.18.1P3D1`）。
> ワークグループ構成の SVM（`Authentication Style: workgroup`）にローカルユーザーを作り、
> Windows Server から SMB でログオン・ログオフ・認証失敗を発生させて EVTX を回収し、
> `python-evtx` でパースして確認しました。**運用設計の部分は測定ではなく、測定結果から導いた
> 設計判断です。** 節ごとにどちらかを明示します。

## 判定に使えるイベントと、その性質

| 用途 | イベント | ユーザー名のフィールド | 性質 |
|---|---|---|---|
| ログオン実績 | 4624 | `TargetUserName` | **SMB セッション単位。ログイン操作の回数ではありません** |
| 実アクセス実績 | 4656 / 4663 | `SubjectUserName` | オブジェクト単位。**NTFS では SACL 必須** |
| 無効化後の生存確認 | 4625 | `TargetUserName` | 認証試行単位 |
| 現在の接続状況 | — | — | `vserver cifs session show`。監査ログではなくこちらを見ます |

**フィールド名がログオン系とファイルアクセス系で違います。** 片方の名前だけで抽出すると無言で 0 件になります。

イベントの記録条件と測定値は
[SMB ログオン監査 — 4624 は記録される](../../security-governance/notes/smb-logon-audit-event-coverage.md)
にあります。

## 4624 だけで判定した場合の誤検知

**Windows から同じ共有を `net use` / `net use /delete` で 3 回繰り返しても、4624 は 1 件でした。** `net use /delete` が解除するのは共有のマッピングで、認証済みセッションは残ります。

この性質は判定を両方向に歪めます。

| 利用パターン | 4624 の増え方 | 棚卸しでの誤り |
|---|---|---|
| 一度接続してセッションを張り続ける | **増えない** | 毎日使っていても「実績なし」と判定される |
| 通信が不安定で再接続を繰り返す | 大量に増える | 実際の利用量より活発に見える |
| 四半期末だけ使う業務アカウント | 期間内に 0 件 | 3 か月窓では「実績なし」 |
| 長期休暇・産休育休中の利用者 | 期間内に 0 件 | 在籍しているのに削除候補 |

**上の 2 行は測定に基づく性質、下の 2 行はその性質から導かれる帰結です。**

対策は判定式を変えることです。

```text
最終利用時刻 = max(
    4624 の TargetUserName ごとの最新 SystemTime,
    4656 / 4663 の SubjectUserName ごとの最新 SystemTime
)
```

**4656 / 4663 のほうが実利用の指標としては素直です。** セッション再利用に影響されません。ただし NTFS ボリュームでは SACL が無いと 1 件も出ないため、**SACL の設定が判定の前提になります。**

## 削除より先に置く無効化

**ここは測定ではなく設計判断です。** 理由が 2 つあります。

1. 前節のとおり、4624 の不在は「使われていない」と同義ではありません
2. ローカルユーザーの削除は取り消せません。そのアカウントをバッチ、スクリプト、スケジュールタスクが使っていた場合、削除は棚卸しではなく障害になります

```text
N 日アクセスなし   → アカウントを無効化（-is-account-disabled true）+ 利用部門へ通知
   ↓ 異議申し立て期間
N+M 日経過かつ申し立てなし → 棚卸し一覧に載せ、承認を得てから削除
```

**無効化には検知の役割もあります。** 無効化したアカウントへのログオン試行は 4625 として記録されるため、**「本当に使われていないか」を能動的に確認できます。** これが誤検知の自動回復ループになり、削除の判断材料にもなります。

無効化は `-is-account-disabled true` で、`local-user show` の `Is Account Disabled` に反映されます。**この項目はオブジェクトが持つ数少ないフィールドの 1 つで、棚卸しの状態を SVM 側に保持できる唯一の場所です。**

## 棚卸しの対象外にする台帳

**設計判断です。** 監査ログだけでは区別できないアカウントがあります。

| 種類 | なぜアクセス実績が出ないか |
|---|---|
| ビルトインの `Administrator` | 通常運用で使わない。ただし削除できない |
| サービスアカウント | アプリケーションが常時セッションを張っていると 4624 が増えない |
| バックアップ用アカウント | 実行間隔が判定窓より長い場合がある |
| マシンアカウント | 人間のアカウントと混ざる |

**クライアント側から見えるユーザー名と、ONTAP が記録するユーザー名は一致しません。** 実測では、Windows の `Get-SmbConnection` がマシンアカウントを表示する一方、ONTAP の 4624 には接続に使ったローカルユーザー名が記録されました。**抽出時にマシンアカウントを明示的に除外してください。**

アカウント発行時に用途・所有者・想定利用頻度を台帳に記録しておくと、監査ログでは判定できない部分が埋まります。**監査ログは「使われた証拠」を示せますが、「もう不要になった」ことは示せません。**

## ワークグループ構成か AD 参加かの選択

**設計判断です。** 本ノートの前提はワークグループ構成（ローカルユーザー）ですが、棚卸しの作り込み量が判断材料になり得ます。

| 観点 | ワークグループ + ローカルユーザー | AD 参加 |
|---|---|---|
| 最終ログオンの取得 | **監査ログの有効化・保管・解析が必要** | AD の `lastLogonTimestamp` |
| AD の可用性への依存 | なし | 生涯続く（[詳細](ad-dependency-lasts-the-lifetime.md)） |
| AD 運用主体との調整 | 不要 | 必要 |
| ユーザーの一元管理 | **SVM ごとに独立**。使い回せない | ドメイン単位 |
| 監査ログ容量の管理責任 | 棚卸しのために負う | 棚卸し目的では不要 |

**どちらが適しているかはアカウント数と増減の頻度で決まります。** ローカルユーザーが数十以上あり異動に伴う増減が頻繁なら AD 参加、少数で固定的ならワークグループと台帳管理、が目安です。**棚卸しの自動化のために監査ログを常時有効化すると、[容量枯渇によるアクセス断のリスク](../../security-governance/notes/audit-log-space-and-client-access.md)を運用に持ち込みます。** そのコストと AD 運用のコストを比べる形になります。

> **可用性に関する補足**: 監査宛先が枯渇したときに止まるのは、**SACL を付けたパスだけ**でした。
> 同一 SVM の監査対象外ボリュームは影響を受けません（実測: 監査対象が拒否されている間に
> 監査対象外へ 5,000 操作が成功）。**つまり棚卸しのために監査を付けた共有こそが、
> 容量枯渇で最初に止まる側になります。** 棚卸しの対象範囲を広げるほど停止する範囲も広がるため、
> SACL は棚卸しに必要なパスに限ってください。

## 段階的な導入

**設計判断です。**

| # | 段階 | ここで分かること |
|---|---|---|
| 1 | 検証 SVM で `cifs-logon-logoff,file-ops` を有効化し 1〜2 週間ログを溜める | 実際の利用パターンでの 4624 の増え方 |
| 2 | 「ユーザー × 最終アクセス時刻」を作り、現場の認識と突き合わせる | **セッション再利用による誤検知の実際の割合** |
| 3 | 宛先ボリュームの増加ペースを測り、保持期間に必要な容量を決める | 容量設計。**有効化前の見積もりでは足りません** |
| 4 | 本番 SVM で有効化。使用率アラームを**先に**入れる | — |
| 5 | 最初の 1 巡は無効化まで自動、削除は手動 | 誤検知率。許容範囲に収まってから自動化を広げる |

**2 を飛ばさないでください。** 誤検知の割合は利用パターン次第で、事前に見積もれません。
