## 匿名化ポリシー（絶対条件）

このディレクトリには **公開できない情報を一切含めません**。判断に迷ったら載せない、が原則です。

| 載せないもの | 代わりに書くもの |
|---|---|
| 企業名・組織名・部門名・製品名 | 業種と規模帯（例: 製造業 / 数百 TB 規模） |
| 担当者名・レビュアー名 | 役割ベースの表記（例: ストレージ運用担当の観点） |
| ホスト名・IP・アカウント ID・ファイルシステム ID | プレースホルダー（`10.0.x.x`、`123456789012`、`fs-0123456789abcdef0`） <!-- gitleaks:allow --> |
| 実際の構成図・スクリーンショットそのまま | 論点が伝わる範囲に抽象化した構成 |
| サポートケース番号・内部チケット ID | 「ベンダーに確認済み（追跡中）」 |
| 組織が特定できる規模・地域・時期の組み合わせ | 粒度を落とす（「2026 年前半」→「直近」） |

**組み合わせによる特定にも注意してください。** 業種・規模・地域・時期をすべて具体的に書くと、個別の項目は匿名でも組織が特定できる場合があります。

公開前チェックは `make audit` で自動化されています。ただし自動チェックは文字列パターンしか見ません。**「この構成を見れば分かる人には分かる」かどうかは人間が判断してください。**

## 書き方

[`_template/case-study.md`](_template/case-study.md) をコピーして書きます。

| セクション | 内容 |
|---|---|
| 状況 | 業種と規模帯のみ |
| 課題 | 何が問題だったか |
| 検討した選択肢 | 採用しなかった案とその理由（トレードオフを対称に） |
| 判断 | 何を選び、なぜそう判断したか |
| 結果 | 何が起きたか。**想定どおりでなかった点も書く** |
| 一般化できる教訓 | 他の環境に持ち出せる部分 |
| 適用条件 | この教訓が当てはまらない条件 |

うまくいった話だけを載せると事例集の価値は落ちます。**想定と違った点、やり直した点こそが読者に有用です。**

## 事例一覧

**2 種類を分けて扱います。**

| 種類 | 内容 | 区分 |
|---|---|---|
| 現場事例 | 技術支援の現場で得た知見を一般化したもの | `field-observation` |
| 検証事例 | **このリポジトリ自身の検証環境での観測。** 顧客案件ではありません | `field-observation` |

検証事例を分けているのは、**読者が「誰の環境の話か」を取り違えないため**です。どちらも 1 つの環境での観測であり、他環境での再現を保証しません。

| 事例 | 種類 | 規模帯 | 主なテーマ |
|---|---|---|---|
| [ドキュメントの既定値が再現せず、その値から導いた設計指針が誤っていた](documented-default-did-not-reproduce.md) | 検証事例 | 数 TB 規模 | 出典があっても実測とは別物。食い違いは両方残す |

**公開されている事例や一次情報を探す場合は** [公開されている一次情報と事例の入口](public-references.md) を参照してください。AWS / NetApp の公式ドキュメント、ブログ、Q&A サイト、コミュニティ発信の**どこに何があるか**と、種類ごとの重みづけを整理しています。
