# 自アカウント開催で詰まる箇所

[🏠 リポジトリトップ](../../../../README.md) | [90 分版シナリオ](README.md)

Workshop Studio が用意するアカウントではなく、**自分のアカウントで**
[このワークショップ](https://catalog.us-east-1.prod.workshops.aws/workshops/9cd82e0b-8348-456b-932a-818b9e5825a1/en-US)
を実行したときに詰まった箇所です。共通しているのは
**エラーメッセージが本当の原因を指していない**ことで、司会者が切り分けを誤ると数分が消えます。

## Glue クローラーは Lake Formation で止まる

90 分版で Glue Data Catalog モジュールを不採用にした理由がこれです。

クローラーは 22.3 秒で終了しましたが、状態は `FAILED` でした。

```text
Insufficient Lake Formation permission(s): Required Describe on <database>
(Service: AWSGlue; Status Code: 400; Error Code: AccessDeniedException)
```

**エラーは S3 Access Point に一言も触れません。** アクセスポイント経由のクロールという珍しい構成なので、
司会者はまずアクセスポイントの権限やエイリアスの綴りを疑います。そこには原因がありません。

原因は、このアカウントで Glue Data Catalog が AWS Lake Formation の管理下にあることでした。
Lake Formation の既定の IAM ベース許可が外れている状態では、新規に作ったクローラー用ロールに
暗黙の `DESCRIBE` が付きません。IAM ポリシーをどう直しても解決しません。

| 確認したこと | 結果 |
|---|---|
| 自分の IAM ユーザーでの `glue create-table` | 成功（0.37 秒） |
| 同じテーブルに対する Athena クエリ 5 本 | すべて成功 |
| クローラー用サービスロールでのクロール | Lake Formation の権限不足で失敗 |
| Lake Formation の権限付与による解消 | **試したが実行できず。** 付与には Lake Formation の管理者権限が必要で、この環境の権限では `Invalid principal` で拒否されました |

つまり**回避策の検証まで到達していません**。分かっているのは、解消には Lake Formation 管理者の関与が
必要で、参加者が自社アカウントで実施する場合その権限を持たない可能性が高いということです。

> **切り分けの補足**: Athena は Glue クローラーなしで成立します。テーブル定義を
> `aws glue create-table` で直接作れば、参加者自身の主体で実行されるため Lake Formation の
> 影響を受けませんでした。90 分版が Athena を採用してクローラーを外したのはこの非対称性によります。

Workshop Studio が払い出すクリーンなアカウントでは Lake Formation が未使用なので、
**本家の手順に不備があるという話ではありません。** 自アカウント開催に固有のリスクです。

## Amazon Quick は IAM だけでは S3 に届かない

**本家のモジュール 08 に書かれていない設定が 1 つあり、これが無いと必ず失敗します。**

本家は 2 つの認可設定を指示します。QuickSight サービスロールへのインラインポリシーと、
アクセスポイントのリソースポリシーです。両方を適用してもナレッジベース作成は次で止まりました。

```text
You do not have permissions to access the S3 bucket.
```

不足していたのは Quick 側のアカウント設定 **「Quick access to AWS services」の Amazon S3** です。
管理画面の Permissions → AWS resources にあり、既定で無効でした。
**IAM ポリシーやアクセスポイントポリシーでは代替できません。**

### 切り分けの決め手

エラー文は「S3 バケット」と言うだけで、アクセスポイントにも設定画面にも言及しません。
アクセスポイント経由という珍しい構成なので、そこを疑って時間を使いがちです。

**新規に作った通常の S3 バケットで試したら、同じエラーになりました。** これで
「アクセスポイント固有の問題ではない」と即座に判定できました。
同じ症状に当たったら、まず**空の普通のバケットで再現するか**を見てください。
再現するなら原因は認可設定であって、アクセスポイントではありません。

### アクセスポイントのエイリアスは一覧に出ない

S3 を有効にするとバケット選択画面が出ますが、**アクセスポイントのエイリアスは列挙されません。**
この画面は実バケットしか一覧しないため、目的の対象が見つからず行き詰まります。

回避策は、同じダイアログの **「S3 Buckets You Can Access Across AWS」タブ →
「Use a different bucket」** の自由入力欄にエイリアスを直接入力することです。
「他アカウントのバケット」という扱いになりますが、同一アカウントのアクセスポイントでも通ります。

### プレフィックス指定ができる場所は 1 箇所だけ

接続設定の「S3 bucket URL」に `s3://<エイリアス>/prefix/` を入れると
`S3 bucket URL must be a valid S3 bucket URL` で拒否されます。ルートしか受け付けません。

絞り込みはナレッジベース作成側の **「Add specific content」** で行います。
ここでは `jaws90/logs/` のようなプレフィックスが通ります。

これは共有ボリュームで実施する場合に効いてきます。ルートを指定すると、
そのアクセスポイントから見える**すべて**が索引対象になります。本家の環境では対象ボリュームに
ログしか置かれていないので問題になりませんが、他の用途と同居させている環境では
索引対象と所要時間の両方が膨らみます。

### 画面の導線が本家と変わっている

本家は「左上の Explore → Knowledge」と書いていますが、現行 UI では
**More → Knowledge** に移動しています。スクリーンショットとクリック経路は一致しません。
司会者は当日ではなく事前に一度たどってください。

## リージョンのハードコードは権限エラーとして現れる

本家は `us-east-1`（または `us-west-2`）を前提にしており、IAM ポリシーとアクセスポイントの
リソース ARN に `us-east-1` が直接書かれています。該当箇所は次のとおりです。

| モジュール | `us-east-1` の出現箇所数 |
|---|---|
| Deploy AgentCore Gateway | 17 |
| Setup Amazon Quick | 9 |
| Create S3 Access Points | 7 |
| Cleanup | 5 |
| Transfer Family (SFTP) | 3 |
| Event-Driven Processing | 2 |
| Glue Data Catalog | 1 |

東京リージョンで実行すると、ARN のリージョン部分が実体と一致しないため、
**アクセス拒否として現れます。「リージョンが違う」とは言ってくれません。**

Workshop Studio のイベントとして開催する場合、イベント側のリージョンが `us-east-1` か `us-west-2` に
なるため整合します。**自アカウントで東京リージョンを使う場合にだけ**、全モジュールの置換が必要です。
事前に済ませる作業として[シナリオ側](README.md#事前に済ませておくこと)にも書いています。

## アクセスポイントのポリシーは追記ではなく置換される

`put-access-point-policy` は**ポリシー文書全体を置き換えます。** 本家のコマンドをそのまま実行すると、
既にそのアクセスポイントに設定されていた許可が黙って消えます。

本家自身がこれを踏んでいます。モジュール 07 はアカウントルートとサービスプリンシパルの
2 ステートメントを設定し、モジュール 08 が同じアクセスポイントに対して
ロール ARN 1 本だけのポリシーを put します。**08 を実行した時点で 07 の設定は残りません。**

既存のアクセスポイントを再利用する場合は、現在のポリシーを取得してからマージしてください。

### 削除済みロールが混ざったポリシーは書き戻せない

マージしようとして次で失敗しました。

```text
MalformedPolicy: Invalid principal in policy
```

原因は**既存ステートメントの主体**でした。ロール ARN ではなく
`AROA...` というユニーク ID の生値が入っていて、`list-roles`（311 件）に該当がありません。
ロールが削除済みで、AWS 側が ARN をユニーク ID に置き換えた状態です。

| 操作 | 結果 |
|---|---|
| `get-access-point-policy` | 成功。ユニーク ID のまま返る |
| 同じ文書を `put-access-point-policy` | **失敗**。ユニーク ID は書き込み時に拒否される |

つまり**読めるが書き戻せないポリシー**が存在します。この状態ではマージが構造的に不可能で、
死んだステートメントを落とすしかありません。落として問題ないことは、
ユニーク ID に対応するロールが存在しないことを `list-roles` で確認して判断しました。

> **運用に関する補足**: ロールを削除する前に、そのロールを主体に指定している
> リソースポリシーを消しておく必要があります。順序を逆にすると、
> 後からそのポリシーを更新できなくなります。アクセスポイントに限らず、
> 主体に ARN を書くリソースポリシー全般に当てはまります。

## IAM ロールの伝播でクローラー作成が数回失敗する

ロールを作った直後に Glue クローラーを作成すると、ロールがまだ引き受け可能になっておらず失敗します。
実測では **3 回目の試行**（約 10 秒の待ち）で成功しました。

手順どおりに続けて実行すると 1 回目で失敗するため、参加者は手順を間違えたと考えます。
コピー＆ペーストで進む場面なので、**司会者から先に「1 回目は失敗します」と言っておく**のが有効です。
これは Glue に限らず、ロール作成の直後にそのロールを使う手順すべてに当てはまります。

## 環境側の落とし穴 — 応答しない NFS マウントが `df` を止める

これはワークショップの問題ではなく、**使い回している検証ホストの問題**です。
同種の環境で実施する人が同じ時間を失わないように記録します。

作業に使った共有 EC2 インスタンスには、応答しないサーバー宛の NFS マウントが `hard` オプションで
残っていました。この状態では、マウントテーブル全体を走査するコマンドが**すべて無期限にブロックします。**

| 使えないコマンド | 代わりに使うもの |
|---|---|
| `df` | `/proc/mounts` を読む |
| `mount`（引数なし） | `grep <対象> /proc/mounts` |
| `mountpoint` | 同上 |
| `du -sh /mnt` | 対象ディレクトリを直接指定する |

本家の手順は `df -h | grep fsx` でマウントを確認させます。**この 1 行で固まります。**
しかも症状はタイムアウトではなく無反応なので、原因がマウント確認コマンド自身にあるとは気づきにくいです。

```bash
grep fsx /proc/mounts || echo "not mounted"
```

新規に用意したインスタンスを使うなら発生しません。使い回すホストで実施する場合は、
**開始前に `grep nfs /proc/mounts` で残存マウントを確認**してください。

## 撤収について

本家の Cleanup モジュールに従います。加えて、検証で作ったものは作った本人が消します。
今回の測定では一時的に作成したアクセスポイント、IAM ロール、Glue のデータベースとテーブル、
Athena のクエリ結果を削除し、共有ホストに追加した NFS マウントも解除しました。
FSx for ONTAP 上のログデータは追試のために残しています。

> **不可逆な操作に関する補足**: このワークショップの採用モジュールに、
> 削除できなくなる設定（SnapLock、Snapshot ロック、オブジェクトロック）は含まれません。
> ハンズオンの題材として不可逆な機能を扱う場合は、
> [SnapLock は有効化とロックが別](../../domains/data-protection/notes/snaplock-and-layered-ransomware-readiness.md)
> を先に読んでください。参加者のアカウントで有効化させる類のものではありません。
