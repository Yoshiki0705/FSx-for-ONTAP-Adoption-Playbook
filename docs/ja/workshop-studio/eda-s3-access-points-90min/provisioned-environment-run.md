# Workshop Studio の払い出し環境で本家の手順を頭から順に実施した記録

[🏠 リポジトリトップ](../../../../README.md) | [90 分版シナリオ](README.md)

AWS Workshop Studio 公開ワークショップ
[FSx for NetApp ONTAP S3 Access Points Workshop](https://catalog.us-east-1.prod.workshops.aws/workshops/9cd82e0b-8348-456b-932a-818b9e5825a1/ja-JP)
を、Workshop Studio が払い出した環境で、日本語版の手順書のとおりに頭から実施した記録です。
[実測値](measured-timings.md) と [自アカウント開催で詰まる箇所](facilitation-risks.md) は自前の東京リージョンの環境で測ったもので、
このノートはその比較対象になります。手順そのものは本家にあるので、ここには本家を読んでも分からないことだけを書きます。

> **記録の範囲に関する補足**: 1 人で 1 回実施した結果です。参加者が数十人いる本番のイベントでは、
> 同じ操作でも待ち時間が変わります。1 回だけ観測した挙動は、本文でその旨を書いています。

## 結論を先に

1. **自アカウント開催の落とし穴は、払い出し環境では出ませんでした。** Glue クローラーは Lake Formation に止められず
   2 分 3 秒で成功し、リージョンも `us-east-1` で本家のポリシー ARN と一致しました。
2. **本家の手順どおりには進まない箇所が 4 か所ありました。** Amazon Quick のアカウント名が既に使われていること（08）、
   Quick Automations にメールの送信手段がないこと（12）、Athena の結果を置く S3 バケットがないこと（13）、
   Lambda の判定が全ログを失敗とすること（15）です。詳細は[本家どおりに進まない箇所](#本家どおりに進まない箇所)。
3. **待ち時間の長さは、自前環境の測定と同じ傾向でした。** Quick のナレッジベースは作成から 16 分以内に利用可能になり、
   データセットの SPICE 取り込みは 7 分 45 秒かかりました。[90 分版](README.md#90-分タイムテーブル)が同期に 25 分を空けている構成は、
   払い出し環境でも変える必要がありません。
4. **AgentCore Gateway 経由の Quick MCP 統合は作成でき、チャットからツールを呼べました。** ただしチャットが答えたログの件数は
   約 289 で、実際の 1,952 と合いません。件数を数えさせる質問は、ハンズオンの題材に向きません。
5. **イベントの終了時刻を過ぎると、画面が開いたままでも AWS API は使えなくなります。** CloudShell に置いたファイルも取り出せません。

## 本家どおりに進まない箇所

### 既に使われている Quick のアカウント名

本家が示すアカウント名 `quick-fsx-ontap-s3-logs` は「指定されたアカウント名は利用できません」で作成できませんでした。
このエラーは、その名前が別のアカウントで使われていることを示しています。**参加者全員が同じ名前を入れると、全員がここで止まります。**
本家にもサフィックスを付ける注意書きはありますが、何を付けるかは書かれていません。開催前に
`quick-fsx-ontap-s3-logs-<suffix>` の `<suffix>` に何を使うか（受付番号など）を決めて伝えてください。

エラーの後で「戻る」を押すと、フォームの入力内容が消えます。アカウント名と通知用メールアドレスを入れ直す必要があります。

### メールの送信手段がない Quick Automations

Automations のアシスタントは計画を立てた後、3 つの質問を返して止まりました。データの場所と形式、
メールの送信手段、送信先です。**払い出し環境にはメールコネクタが設定されておらず、本家の「メールを確認してください」は成立しません。**

メールを使わずに要約を実行結果として出すよう回答すると、計画は 2 ステップに改訂され、構築まで進みました。
しかしテストは 2 回とも最初のステップのデータ読み込みで `NATIVE_FILE.InvalidInput`（File not found）になりました。
アシスタントが Quick のデータセットではなく、オートメーショングループの共有ストレージのファイルを読むコードを作ったためです。
グループの「Shared files」にデータセットを追加しても解消しませんでした（1 回の実施で観測）。
アシスタントとの 1 往復には 1〜10 分かかります。

90 分版はこのモジュールを不採用にしています。採用するなら、データの渡し方とメールの扱いを手順として先に固定する必要があります。

### 結果の保存先がない Athena

Query editor は初回に「結果の場所を設定する必要があります」と表示します。**払い出しアカウントには S3 バケットが 1 つもありません。**
本家の「アカウントで利用可能な任意の S3 バケット」は存在しないので、参加者は止まります。

今回はバケットを作らず、S3 Access Points のエイリアス `s3://<alias>/athena-results/` を結果の保存先にしました。
クエリ結果の書き込みも成功し、結果は FSx for ONTAP の `logs` ボリュームに書かれます。この方法には副作用があり、
AgentCore Gateway のツールでファイル一覧を取ると `athena-results/` のファイルも混ざります。
[90 分版の事前作業](README.md#事前に済ませておくこと)にある「結果の出力先バケットを用意」は、払い出し環境でも必要です。

### 全ログを失敗と判定する Lambda

Event-Driven Processing の Lambda 関数は、ログの本文に `UVM_FATAL` という文字列があるかどうかで重大な失敗を判定します。
**シミュレーションログには成功時も `UVM_FATAL :  0` の行があるため、20 件すべてを失敗と判定しました。**
同じ 20 件のうち実際に失敗していたのは 9 件です。参加者が「失敗が多すぎる」と感じたときの説明として知っておくと、
時間を失いません。

### 置換されるアクセスポイントのポリシー

モジュール 08 の `put-access-point-policy` がモジュール 07 のポリシーを丸ごと置き換える点は、
[自アカウント開催の記録](facilitation-risks.md#追記ではなく置換されるアクセスポイントのポリシー)と同じでした。
払い出し環境では、置き換えた後も参加者ロールでの Athena、Glue、AgentCore、Lambda、Transfer Family の操作は通りました。
サービスプリンシパルの文が消えた状態で各サービスがどの権限で動いたかは、確認していません。

## Quick MCP 統合の画面と挙動

AgentCore Gateway の最後の 2 ステップ（Quick MCP 統合とエージェントクエリのテスト）で、本家の記述と違った点です。

| 項目 | 実際の挙動 |
|---|---|
| ウィザードの段数 | 5 段（接続、認証、書き込み権限の管理、読み取り権限の管理、Publish）。本家にない「書き込み権限の管理」（0 件）が挟まる |
| 認証の選択肢 | 「サービス認証」を選ぶと「サービス間 OAuth」になる。クライアント ID、クライアントシークレット、トークン URL の 3 項目 |
| クライアントシークレットの入力欄 | 伏せ字にならない。画面共有や録画をしている参加者は値が映る |
| トークン URL | Cognito のドメインにアカウント ID が入る（`eda-agentcore-gateway-<アカウント ID>.auth...`）。画面を共有するときは伏せる |
| Publish 画面の注意書き | サービス間認証の接続はチャットやフローで使えない、という趣旨の英文が出る。実際にはチャットからツールを呼べた |
| チャットの対象の指定 | 入力欄の下の「すべてのデータ」→「特定のデータ」→「アクション」タブで EDA Logs Agent を選ぶ |
| 送信 | Enter キーで送信されないことがあり、送信ボタンを押した |

チャットのテスト 4 問の結果です。

| テスト | 呼ばれたツール | 応答時間 | 結果 |
|---|---|---|---|
| 1. ログファイルの一覧と種類別の件数 | `list_objects` | 50 秒 | 件数を約 289 と回答（実際は 1,952） |
| 2. 1 ファイルを読んで合否を判定 | `read_object` | 30 秒 | ログの結果 `PASS` を正しく回答 |
| 3. タイミング違反のジョブを探し 3 種類のログを突き合わせる | 複数回 | 56 秒 | job 0008 の 3 ログを読み、原因を説明 |
| 4. 全シミュレーションの合否比率とモジュール別の失敗率 | 複数回 | 55 秒 | 約 14 ファイルを読んだところで、Research タスクに切り替えるかを質問して止まった |

**件数のずれは 1 回の実施で観測したもので、原因は確認していません。** ツールの 1 回の応答に全件が入っていないと考えていますが、
Lambda のページング処理は読んでいません。テストアクション API で `Prefix` に `simulation_` を入れても、
`athena-results/` のオブジェクトが先頭に返りました。Prefix が Lambda に渡っていない可能性があります（未確認）。

| 本家の表記 | 日本語 UI の表示 |

| More > Knowledge | さらに詳しく > ナレッジ |
| More > Connectors | さらに詳しく > コネクタ |

| Service Authentication | サービス認証 |

| Chat Agents | チャットエージェント |
| Specific data | 特定のデータ |

コンソールの検索で出る名前は「AWS Quick」で、同じ検索結果に「QuickSight」も並びます。

`service-role/aws-quicksight-service-role-v0`（services ではなく service）です。

## 払い出し環境に固有の事情

| 事情 | 影響 | 対処 |
|---|---|---|
| ボリュームが各 10 GiB | `df -h` の表示が各 9.5G で、本家の例（973G / 487G）と合わない | 失敗ではないと先に伝える |
| EC2 が 2 台 | 本家は「単一の EC2」と書く。2 台目は使われない | 参加者が迷ったら 1 台目だけを使うと伝える |
| CloudShell は操作がないと再起動する | 環境変数が消え、本家のコマンドが空の値で動く。今回 1 回発生 | 「値が空ならセットアップの変数ブロックを貼り直す」を先に伝える |
| EC2 のシェルに CloudShell の変数がない | マウントの `$FSX_DNS` が空になり失敗する | CloudShell で表示した値を手で貼る |
| 複数行の貼り付けに確認ダイアログが出る | 長いヒアドキュメントの手順（03、06、07、09、13）で止まる | ダイアログの「貼り付け」を押す |
| fsxadmin のパスワードが未設定 | 本家の範囲では影響しない。ONTAP CLI や REST を使う追加の確認には事前の設定が要る | 必要なときだけ設定する |
| S3 コンソールの「アクセスポイント」一覧に出ない | 作成に失敗したと誤解する | 左メニューで、通常の「アクセスポイント」とは別に並ぶ FSx for ONTAP 向けのアクセスポイント一覧を見る |

イベントの終了時刻を過ぎた後の挙動も確認しました。画面は開いたまま残りますが、`aws sts get-caller-identity` が
`InvalidClientTokenId` を返します。CloudShell は再読み込みすると環境を作成できなくなり、エラーが案内する
「アクション > 再起動」はボタンが無効で押せませんでした。Quick を再読み込みすると AWS のサインインページに移ります。
**終了前に、参加者が残したいものを手元にダウンロードさせてください。**

## 本家にない追加の確認

ワークショップの範囲外で、同じ環境の ONTAP REST API（CloudShell から EC2 経由の SSM ポート転送）で確かめたことです。
いずれも 1 回の実施です。

| 確認したこと | 結果 |
|---|---|
| ONTAP のバージョン | `GET /api/private/cli/version?fields=version` で 2 ノードとも 9.18.1P8HF2。`fields` を付けないとノード名だけが返る。`verbose=true` は `Unexpected argument "verbose"` で拒否された |
| ボリューム作成と SnapMirror | DP ボリューム（1 GiB）を作り、`logs` からの SnapMirror を作成した。作成時に `state: snapmirrored` を同時に指定すると拒否され、作成後に PATCH で `state` を `snapmirrored` にすると初期化された（転送 success、lag 20 秒） |
| FlexCache | 同じ SVM の `logs` をオリジンに、FlexCache ボリューム（1 GiB）を作成できた。ONTAP 上の表示は FlexGroup スタイル |
| ONTAP で作ったボリュームの Amazon FSx の API への反映 | 作成要求から 7 分間、`aws fsx describe-volumes` の結果に 2 本とも出なかった。それ以降はイベント終了で確認できていない |

## 自前環境の測定との比較

同じ操作を、[2026-08 の自前環境の測定](measured-timings.md)と並べます。環境が違うので、差は環境の差を含みます。

| 操作 | 自前環境（ap-northeast-1、Single-AZ、128 MBps） | 払い出し環境（us-east-1、マルチ AZ、512 MBps） |
|---|---|---|
| EDA ログ生成 | 2.50 秒 | 6 秒 |
| アクセスポイント作成から `AVAILABLE` | 14.27 秒 | 46 秒 |
| ナレッジベースの同期完了 | 11.5〜14.1 分 | 16 分以内（途中の確認なし） |
| Athena のクエリ 1 本 | 実時間 2〜3 秒 | 画面の実行時間 1.0〜1.3 秒 |
| Glue クローラー | 22.3 秒で失敗（Lake Formation） | 2 分 3 秒で成功 |
