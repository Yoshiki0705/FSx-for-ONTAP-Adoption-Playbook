| 項目 | 値 |
|---|---|
| 測定日 | 2026-08-07（UTC） |
| リージョン | ap-northeast-1 |
| ファイルシステム | Amazon FSx for NetApp ONTAP、Single-AZ、SSD 1,024 GiB、スループット 128 MBps |

## FSx for ONTAP 側の操作

| 操作 | 本家の記載 | 実測 |
|---|---|---|
| EDA ログ生成（500 ジョブ / 1,952 ファイル / 3.35 MiB） | 「約 90 秒」、モジュール枠 10 分 | **2.50 秒** |
| 集計 CSV 生成（500 行 32 列 / 85 KB） | 記載なし（モジュール枠 20 分の一部） | **1.20 秒** |
| 集計 CSV を `csv/` サブディレクトリへコピー | 記載なし | 0.22 秒 |

生成されたファイルの内訳は LSF ジョブログ 500、コンパイルログ 498、シミュレーションログ 482、
後処理ログ 472 で、平均 1.8 KiB でした。本家のスクリプトは `random.seed(42)` を使うため、
**この 1,952 という数は再現します**。人数分の容量見積もりに使えます。

**公称 90 秒との差は約 36 倍です。** 2 vCPU で 1,952 個の小さなファイルを NFSv3 経由で書く処理が
2.5 秒で終わるため、このモジュールに 10 分を割り当てる必要はありません。
[90 分版](README.md#90-分タイムテーブル)では 8 分に圧縮し、うち大半をログの中身を読む時間に充てています。

## S3 Access Point の操作

| 操作 | 実測 |
|---|---|
| アクセスポイント作成 → `AVAILABLE` | **14.27 秒**（API 応答自体は 0.81 秒） |
| アクセスポイントのデタッチ完了 | 13.99 秒 |
| `HeadBucket` | 0.75 秒 |
| `ListObjectsV2` 1 ページ（1,000 キー） | 1.22 秒 |
| 全 1,952 キーの一覧（ページング込み） | 1.53 秒 |
| `GetObject` 1 件（約 2 KiB のログ） | 0.27 秒 |
| 全 1,952 ファイルのダウンロード | 14.70 秒 |

NFS で書き込んだ直後のファイルが、待ち時間なしに S3 API から見えました。
ワークショップの主題である「コピーもしない、同期もしない」はこの 2 つの数字の並びで示せます。

**同一アカウントからの参照にアクセスポイントのリソースポリシーは不要でした。** 測定に使ったアクセスポイントには
別の主体を許可するポリシーが付いていましたが、こちらの IAM ユーザーは許可対象に含まれていません。
それでも ID ベースのポリシーだけで `ListObjectsV2` と `GetObject` が成功しました。
本家がポリシーを設定するのは、Amazon Quick のサービスロールという**別の主体**に許可を出すためです。

## Amazon Quick のナレッジベース

**このモジュールがタイムテーブル全体を支配します。** 本家の記載と実測が最も大きくずれた箇所です。

| 段階 | 本家の記載 | 実測 |
|---|---|---|
| 作成 API が `Status: ACTIVE` を返すまで | 「作成 30 秒」 | **16.4 秒** |
| 画面上の同期完了（`Sync status` が `Completed` になる） | 「同期 3〜5 分」、別の箇所では全体で「5〜10 分」 | **11.5〜14.1 分**（11.5 分時点で `In progress`、14.1 分時点で `Completed` を観測） |
| 同期完了後の自然言語質問への応答 | 記載なし | **54 秒以内** |

対象は S3 Access Point 経由の 1,954 ファイル（ログ 1,952 + 集計 CSV + 派生分）です。
ポーリング間隔の都合で完了時刻は 11.5〜14.1 分の区間としてしか特定できていません。

**本家の記載を上回りました。** 「3〜5 分」は明確に外れ、「5〜10 分」も超えています。
90 分構成でこのモジュールを扱うなら、記載値ではなくこの実測値で枠を取ってください。

**`Status: ACTIVE` は準備完了を意味しません。** これは重要な区別です。

| 確認方法 | 16 秒時点の応答 |
|---|---|
| `aws quicksight list-knowledge-bases` | `Status: ACTIVE` |
| 画面の `Status` 列 | `Syncing` |
| 画面の `Sync status` 列 | `In progress` |

API だけを見て「できた」と判断すると、まだ答えられないナレッジベースに質問することになります。
[FSx for ONTAP S3 AP で `HeadBucket` が成功してもデータ操作が失敗する](../../domains/data-utilization/notes/s3-access-point-constraints.md)
のと同じ構造の落とし穴で、**成功を報告する API と、実際に使える状態が別**です。

この実測を踏まえて[タイムテーブル](README.md#90-分タイムテーブル)は、同期開始を経過 40 分の時点に置き、
Quick で質問する時間までに **25 分の間隔**を確保しています。本家記載の 5〜10 分を信じて
15 分しか空けない構成にすると、間に合わない可能性があります。

### 回答内容の正しさを検証した

速さだけでなく、答えが合っているかも確かめました。質問は
「ライセンス取得失敗で落ちたジョブはどのライセンス機能に関係しているか、件数も」です。

| ライセンス機能 | Quick の回答 | 集計 CSV の実際の値 |
|---|---|---|
| Verilog_Compiler | 6 | 6 |
| IMC_Coverage | 5 | 5 |
| Specman_Elite | 4 | 4 |
| Xcelium_ML | 1 | 1 |
| NC_Elaborator | 1 | 1 |
| 合計 | 17 | 17 |

**完全に一致しました。** 回答には根拠として `lsf_job_0403.log` など個別のログファイル名が示され、
FlexNet ライセンスサーバーで利用可能数が 0 だったという原因まで含まれていました。

> **数え方に関する補足**: 同じデータに「ライセンス失敗の件数」の解釈が 2 つあります。
> `license_feature` に値が入っている行は 17 件ですが、`failure_type` が `License Failure` の行は
> 10 件です。ライセンス起因の失敗がコンパイル段階とシミュレーション段階のどちらでも起こり、
> 集計時の分類が変わるためです。Quick は前者の解釈を採りました。どちらも妥当なので、
> **参加者に見せるときは「どちらの数を聞いているか」を明示する**と混乱を避けられます。
> 正確な数が要るなら Athena で定義を書いて数えるのが確実で、
> これは Athena モジュールを残す理由にもなります。

### 3 つの実施形態と見積もり

| 形態 | 内容 | 見積もり |
|---|---|---|
| A. 全部を参加者が構築 | 本家の Step 1〜8 をそのまま | **35〜45 分** |
| B. ゲートウェイを事前構築 | Step 1〜6 を開催前に済ませ、当日は Step 7〜8 | **15〜20 分** |
| C. 講師の実演のみ | 構築済みを見せて質問を 2 本流す | **8〜10 分** |

形態 A の内訳は次のとおりです。

| ステップ | 作業量 | 見積もり |
|---|---|---|
| Step 1 CLI 確認・更新 | コマンド 2 本 | 1〜4 分 |
| Step 2 スタック作成 | **254 行のテンプレートを貼り付け** + 待ち | 6〜9 分 |
| Step 3 出力の取得 | 環境変数への設定 | 2 分 |
| Step 4 ゲートウェイ作成 | コマンド 2 本 + 待ち | 3〜4 分 |
| Step 5 MCP ツール登録 | JSON スキーマ 3 本（`list_objects` / `read_object` / `search_objects`） | 5〜7 分 |
| Step 6 疎通確認 | 任意。省略可 | 0 分 |
| Step 7 Quick の MCP 連携 | 画面操作 7 箇所 + Cognito の資格情報入力 | 5〜8 分 |
| Publishing 待ち | — | 2〜3 分 |
| Step 8 エージェント的質問 | 4 本 | 6〜10 分 |

**形態 A の最大のリスクは Step 2 です。** 254 行のテンプレートを人数分だけ貼り付けるので、
必ず失敗する参加者が出ます。集団での実施では最も遅い人がペースを決めるため、
上限側（45 分）で見ておくのが安全です。

### 90 分への収まり

現行のタイムテーブルの余裕は 01:00 の 5 分枠だけなので、**形態 A は入りません。**

形態 B（15〜20 分）を入れるなら、**Quick のナレッジベース同期を開催前に済ませる**のが前提です。
同期を事前化すると Athena に持たせていた「同期待ちを埋める」役割が不要になり、
Athena 15 分と集計 CSV 5 分の計 20 分が空きます。ここを AgentCore と入れ替えられます。

ただし交換には失うものがあります。Athena を外すと「同じデータが SQL からも読める」という
多用途性の話ができなくなり、[AI の回答が正確かを検証する](#回答内容の正しさを検証した)場面も無くなります。
**AI エージェントを見せるか、AI の答え合わせを見せるか**の選択になります。

形態 C（8〜10 分）なら、01:00 の 5 分枠を潰し、Athena のクエリを 5 本から 3 本に減らせば収まります。
「紹介する」ことが目的なら、こちらが 90 分への影響が最も小さい選択です。
